## Concept
`chall4.exe`는 이전에 다룬 [XOR 인코딩 crackme]와 구조는 동일하지만, 입력값에 적용되는 연산이 **비트 시프트와 OR 조합**으로 바뀐 문제이다. 하드코딩된 값과 입력값을 특정 연산으로 변환한 결과를 비교한다는 큰 틀은 같고, **역연산 수식을 새로 세워야 한다**는 점만 다르다.

## 서비스 분석
### `main`
![main](/assets/img/posts/rev4/main.png)

`main`은 입력을 받은 뒤 `sub_140001000`을 호출하고, 반환값을 `test`로 검사해 0이면 `"Wrong"`, 0이 아니면 `"Correct"`를 출력한다. 이전 문제와 동일한 구조이므로, 검증 로직은 `sub_140001000` 내부를 봐야 한다.

### 검증 함수 — `sub_140001000`
![sub](/assets/img/posts/rev4/sub_140001000.png)

디컴파일 결과는 다음과 같다.

```c
__int64 __fastcall sub_140001000(__int64 a1)
{
  int i; // [rsp+0h] [rbp-18h]

  for ( i = 0; (unsigned __int64)i < 0x1C; ++i )
  {
    if ( ((unsigned __int8)(16 * *(_BYTE *)(a1 + i)) | ((int)*(unsigned __int8 *)(a1 + i) >> 4)) != byte_140003000[i] )
      return 0;
  }
  return 1;
}
```
{: file="sub_140001000_pseudocode.c"}

XOR 연산 문제보다 식이 조금 복잡해졌지만, 자세히 보면 이렇다.

* `16 * *(_BYTE*)(a1+i)` → 입력 바이트를 8비트 범위 내에서 왼쪽으로 4비트 시프트(하위 니블을 상위 니블 자리로 이동, `unsigned __int8` 캐스팅으로 상위 비트는 잘려나감)
* `*(unsigned __int8*)(a1+i) >> 4` → 입력 바이트를 오른쪽으로 4비트 시프트(상위 니블을 하위 니블 자리로 이동)
* 이 둘을 `OR`로 합치면 결과적으로 **한 바이트 안에서 상위 니블과 하위 니블의 위치를 서로 맞바꾸는(니블 스왑) 연산**이 된다.

즉 `입력값의 니블을 스왑한 결과`가 `byte_140003000[i]`와 같아야 `Correct`가 나오는 구조다.

## 익스플로잇
### 역연산 도출
비교 수식을 정리하면 다음과 같다.

```
byte_140003000[i] = (A << 4 | A >> 4)   // A = input[i], 니블 스왑
```

핵심은 **니블 스왑은 그 자체로 자기 자신의 역연산**이라는 점이다. 한 바이트를 니블 스왑하면 상위·하위 니블이 한 번 뒤바뀌고, 그 결과를 다시 한 번 니블 스왑하면 원래 위치로 돌아온다(스왑을 두 번 적용하면 항등 변환). 따라서 하드코딩된 값에 **같은 연산을 한 번 더 적용**하기만 하면 원본 입력값을 그대로 복원할 수 있다.

```
input[i] = (byte_140003000[i] << 4 | byte_140003000[i] >> 4)  // = A*16 | A/16, 단 상위비트는 0xFF로 마스킹
```

### 익스플로잇 스크립트
```py
byte_140003000 = [
    0x24, 0x27, 0x13, 0xC6, 0xC6, 0x13, 0x16, 0xE6, 0x47, 0xF5,
    0x26, 0x96, 0x47, 0xF5, 0x46, 0x27, 0x13, 0x26, 0x26, 0xC6,
    0x56, 0xF5, 0xC3, 0xC3, 0xF5, 0xE3, 0xE3
]

flag = ""
for val in byte_140003000:
    original_byte = ((val * 16) & 0xFF) | (val // 16)
    flag += chr(original_byte)

print(flag)
```
{: file="exploit.py"}

`val * 16`은 왼쪽으로 4비트 시프트한 것과 같은데, 파이썬의 정수는 비트폭 제한이 없어 시프트 후에도 상위 비트가 그대로 남아있다. 원래 바이너리에서는 `unsigned __int8` 캐스팅으로 이 상위 비트가 잘려나갔으므로, 스크립트에서도 `& 0xFF`로 상위 비트를 직접 날려줘야 원본과 동일한 결과가 나온다. 이 마스킹을 빼먹으면 값이 밀려서 잘못된 문자가 나오게 된다.

## 정리
* 시프트 + OR로 조합된 연산이라도, 그 조합이 **니블 스왑처럼 자기 자신이 역연산인 경우**에는 별도의 역함수를 유도할 필요 없이 같은 연산을 한 번 더 적용하면 된다.
* C의 `unsigned __int8` 같은 크기 캐스팅은 상위 비트를 자동으로 잘라내는데, 파이썬 등 비트폭 제한이 없는 언어로 역연산 스크립트를 짤 때는 **이 마스킹 과정을 직접 재현(`& 0xFF`)해줘야** 원본 바이너리와 동일한 결과를 얻을 수 있다.
