## Introduction

네트워크에 새로운 장치를 연결할 때마다 IP 주소, 서브넷 마스크, 게이트웨이, DNS 서버를 일일이 수동으로 입력하는 것은 장치 수가 많아질수록 비효율적이고 실수(주소 중복 등)로 이어지기 쉽다. 이런 문제를 해결하기 위해 등장한 것이 **DHCP(Dynamic Host Configuration Protocol)**이다. 이번 글에서는 DHCP의 동작 원리를 정리하고, Cisco Packet Tracer로 직접 DHCP 서버를 구성해 실습해본다.

### Concept: DHCP란

DHCP는 IP 네트워크에서 장치들을 자동으로 식별하고 설정하게 해주는 **관리형 프로토콜**이다. 클라이언트가 네트워크에 연결되면 DHCP를 통해 다음 정보를 자동으로 받는다.

1. IP Address
2. Subnet Mask
3. Default Gateway
4. DNS Server

IP 주소를 자동으로 부여하면 네트워크 관리가 단순해질 뿐 아니라, **주소의 유일성(Uniqueness)** 을 보장해 중복·충돌을 예방할 수 있다. 또한 더 이상 네트워크에 연결되지 않은 장치의 주소는 회수해 재사용하므로, 사용 가능한 주소 풀(Pool)을 효율적으로 관리할 수 있다.

할당받은 IP 주소에는 **Lease Time(임대 시간)** 이 있어, 이 시간이 지나면 클라이언트가 다시 IP를 할당받아야 한다. 임대 시간이 만료되기 전 클라이언트가 동일한 IP를 계속 쓰고 싶다면 임대 연장을 요청하는데, 이 과정을 **Renew**라고 부른다.

## Mechanism: DORA 프로세스

클라이언트와 DHCP 서버는 4단계의 메시지 교환을 통해 IP 할당을 완료한다. 이 순서를 각 단계의 앞글자를 따 **DORA(Discover → Offer → Request → Acknowledge)** 라고 부른다.

| 구성 요소 | 역할 |
| :--- | :--- |
| **DHCP Server** | IP 주소 할당을 수행하는 라우터 또는 서버형 네트워크 장비. 사용 가능한 IP 주소 풀을 관리하고 각종 파라미터를 구성함 |
| **Client** | 네트워크에 연결되어 DHCP에 요청을 보내는 모든 장치 |

#### 1. Discover
장치가 네트워크에 연결되면, 가용한 DHCP 서버를 찾기 위해 **DHCP Discover** 메시지를 브로드캐스트한다.

#### 2. Offer
Discover 메시지를 수신한 DHCP 서버가 클라이언트에게 할당 가능한 IP 주소를 담아 **DHCP Offer** 메시지로 응답한다.

#### 3. Request
클라이언트가 Offer를 받고, 해당 IP 주소를 사용하겠다는 의사를 담아 **DHCP Request** 메시지로 응답한다.

#### 4. Acknowledge
DHCP 서버가 **DHCP Acknowledge** 메시지를 보내 클라이언트에게 IP 주소가 최종 할당되었음을 확인해준다. 이 시점부터 클라이언트는 해당 IP 주소로 다른 네트워크 장치와 통신할 수 있다.

## 요약

* **본질**: DHCP는 클라이언트에게 IP/서브넷 마스크/게이트웨이/DNS를 자동으로 할당해 네트워크 관리를 단순화하고 주소 충돌을 예방하는 프로토콜이다.
* **핵심 절차**: Discover(찾기) → Offer(제안) → Request(요청) → Acknowledge(확정)의 4단계 브로드캐스트/응답 교환으로 IP 할당이 완료된다.

## 한계와 대안: 라우터 기반 DHCP

Server 장비로 DHCP 서버를 구현하면 GUI로 설정이 간편하다는 장점이 있지만, **Lease Time(임대 시간)을 별도로 구현할 수 없다**는 한계가 있다. 실제 DHCP 서버처럼 임대 시간을 지정하고 싶다면 라우터의 CLI를 이용해 DHCP를 구성해야 한다.

```
Router> enable
Router# configure terminal

! 1. 라우터 자체 인터페이스(포트) IP 설정 및 활성화
Router(config)# interface gigabitEthernet 0/0
Router(config-if)# ip address 192.168.1.1 255.255.255.0
Router(config-if)# no shutdown
Router(config-if)# exit

! 2. 자동 할당에서 제외할 IP 지정 (라우터 IP 보호)
Router(config)# ip dhcp excluded-address 192.168.1.1 192.168.1.10

! 3. DHCP 풀(Pool) 생성 및 네트워크 범위 지정
Router(config)# ip dhcp pool OFFICE_NETWORK
Router(dhcp-config)# network 192.168.1.0 255.255.255.0

! 4. 게이트웨이 및 DNS 주소 지정
Router(dhcp-config)# default-router 192.168.1.1
Router(dhcp-config)# dns-server 8.8.8.8

! 5. 임대 시간(Lease Time) 설정 
Router(dhcp-config)# lease 0 12 0
Router(dhcp-config)# exit
```
{: file="router.txt"}

Lease 명령어는 `lease [일] [시간] [분]` 형식으로 입력한다.

* `lease 0 12 0` → 12시간 동안 IP를 임대
* `lease 1 0 0` → 1일(24시간) 동안 IP를 임대
* `lease infinite` → 만료 시간 없이 무제한으로 임대

즉, GUI 기반 Server 장비는 빠른 구성에 적합하고, Lease Time까지 포함한 실제 운영 환경에 가까운 DHCP 동작을 재현하려면 라우터의 `ip dhcp pool` 설정을 사용하는 것이 적절하다.

## 확장: DHCP Relay Agent

### Concept: 왜 필요한가
지금까지의 실습은 DHCP 서버와 클라이언트가 **같은 네트워크(같은 브로드캐스트 도메인)** 에 있는 경우였다. DORA 과정의 시작인 **Discover 메시지는 브로드캐스트**로 전송되는데, 브로드캐스트는 기본적으로 라우터를 넘어가지 못한다. 라우터는 서로 다른 브로드캐스트 도메인(서브넷)을 분리하는 장비이기 때문이다.

그런데 실제 기업 네트워크에서는 관리 편의를 위해 DHCP 서버 한 대를 두고, 여러 서브넷(VLAN)의 클라이언트들이 이 서버 하나를 공유하는 구조가 일반적이다. 이 경우 클라이언트의 Discover 브로드캐스트가 다른 서브넷에 있는 DHCP 서버까지 도달하지 못하는 문제가 생긴다. 이를 해결하는 것이 **DHCP Relay Agent**다.

### Mechanism: ip helper-address

DHCP Relay Agent는 보통 클라이언트와 같은 서브넷에 있는 **라우터(정확히는 라우터의 해당 인터페이스)** 가 담당한다. 동작 방식은 다음과 같다.

1. 클라이언트가 DHCP Discover를 브로드캐스트로 전송한다.
2. 이 브로드캐스트를 수신한 라우터(Relay Agent 역할)가 패킷을 폐기하지 않고, **유니캐스트로 변환**해 지정된 DHCP 서버 주소로 직접 전달한다. 이때 라우터는 자신의 IP(클라이언트가 속한 서브넷의 게이트웨이 주소)를 `giaddr`(Gateway IP Address) 필드에 채워 넣는다.
3. DHCP 서버는 `giaddr` 값을 보고 **어느 서브넷에서 온 요청인지 판단**해, 그 서브넷에 맞는 주소 풀에서 IP를 할당한 Offer를 다시 라우터에게 유니캐스트로 보낸다.
4. 라우터는 이 Offer를 받아 원래 클라이언트가 속한 서브넷으로 다시 전달(필요 시 브로드캐스트)한다.
5. 이후 Request/Acknowledge도 동일하게 라우터를 거쳐 중계된다.

즉 Relay Agent는 **DHCP 서버 입장에서는 클라이언트를, 클라이언트 입장에서는 DHCP 서버를 대신하는 중계자** 역할을 한다.

### 설정 예시

예를 들어 클라이언트가 있는 서브넷(`192.168.10.0/24`)의 게이트웨이 라우터에서, 다른 서브넷(`10.0.0.5`)에 있는 DHCP 서버로 요청을 중계하려면 클라이언트 쪽 인터페이스에 `ip helper-address`를 설정하면 된다.

```
Router> enable
Router# configure terminal

! 클라이언트가 연결된 인터페이스로 진입
Router(config)# interface gigabitEthernet 0/1
Router(config-if)# ip address 192.168.10.1 255.255.255.0
Router(config-if)# no shutdown

! 이 인터페이스로 들어오는 DHCP 브로드캐스트를
! 지정한 DHCP 서버(10.0.0.5)로 유니캐스트 릴레이
Router(config-if)# ip helper-address 10.0.0.5
Router(config-if)# exit
```
{: file="relay_router.txt"}

`ip helper-address`는 DHCP 브로드캐스트(UDP 67/68)뿐 아니라 TFTP, DNS 등 몇 가지 다른 브로드캐스트 기반 프로토콜도 함께 중계 대상에 포함시킨다는 점도 참고할 만하다.

### 서버 측 고려사항
DHCP 서버는 `giaddr` 값을 기준으로 요청이 어느 서브넷에서 왔는지 구분하므로, 서버에는 **서브넷별로 별도의 DHCP 풀**이 구성되어 있어야 한다. 예를 들어 라우터 기반 설정이라면 서브넷마다 `ip dhcp pool`을 따로 만들고 각 풀의 `network` 범위를 해당 서브넷에 맞게 지정해야, Relay를 통해 들어온 요청에 대해 올바른 서브넷의 주소를 할당할 수 있다.

```
Router(config)# ip dhcp pool SUBNET_10
Router(dhcp-config)# network 192.168.10.0 255.255.255.0
Router(dhcp-config)# default-router 192.168.10.1
Router(dhcp-config)# exit

Router(config)# ip dhcp pool SUBNET_20
Router(dhcp-config)# network 192.168.20.0 255.255.255.0
Router(dhcp-config)# default-router 192.168.20.1
Router(dhcp-config)# exit
```

### 정리
* 브로드캐스트 기반인 DHCP Discover는 기본적으로 라우터를 넘지 못하기 때문에, 서버와 클라이언트가 다른 서브넷에 있을 때는 **Relay Agent**가 필요하다.
* 클라이언트 쪽 게이트웨이 라우터에 `ip helper-address <DHCP서버IP>`를 설정하면, 라우터가 브로드캐스트를 유니캐스트로 바꿔 DHCP 서버로 중계해준다.
* DHCP 서버는 릴레이된 요청의 `giaddr` 값을 보고 알맞은 서브넷의 주소 풀에서 IP를 할당하므로, 서버 쪽에도 서브넷별 풀 구성이 필요하다.

>DHCP Relay 실습은 진행후에 추가할거임
