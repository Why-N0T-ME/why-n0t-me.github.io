## Concept - Frida Mode Fuzzing
AFL++의 Frida 모드는 소스코드가 없는 실행 파일 내부를 들여다보기 위해 Frida의 Stalker 기능을 활용한다. 바이너리가 실행될 때 기본 블록(Basic Block) 단위로 코드를 추적하고, 실행 흐름(Edge) 정보를 AFL++의 공유 메모리 비트맵에 실시간으로 기록하여 효율적인 Mutation(변이) 퍼징을 가능하게 만든다.

바이너리만 제공되어 소스코드를 볼 수 없는 상황임에도 불구하고, 내부 실행 경로 피드백을 실시간으로 추적하므로 완전한 Black-box가 아닌 **지능형 그레이박스 퍼징(Grey-box Fuzzing)**을 수행할 수 있다는 것이 최고의 핵심 장점이다.

### Target Binary
소스코드가 없는 레거시 바이너리 상황을 연출하기 위해, AFL 전용 컴파일러 대신 일반 `gcc`로 컴파일을 진행한다. 문자열 첫 두 글자가 `FU`일 때 의도적으로 **널 포인터 역참조(Null Pointer Dereference)** 세그멘테이션 결함이 터지도록 설계한 코드다.

```c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

void fuzz_me(char *buf) {
    // 인덱스를 기반으로 문자를 정확히 검사하도록 구성
    if (buf[0] == 'F') {
        if (buf[1] == 'U') {
            printf("[!] Crash triggered via Null Pointer Dereference!\n");
            int *ptr = NULL;
            *ptr = 1337; // 널 포인터 역참조 유도 (SIGSEGV)
        }
    }
}

int main(int argc, char *argv[]) {
    if (argc < 2) return 1;

    // 인자로 넘어온 변이 파일 경로 열기
    FILE *fp = fopen(argv[1], "r");
    if (!fp) return 1;

    char buf[100] = {0}; // 넉넉한 정상 크기의 입력 버퍼
    if (fgets(buf, sizeof(buf), fp) != NULL) {
        fuzz_me(buf);
    }

    fclose(fp);
    return 0;
}
```

### Frida 계측 스크립트의 필요성과 효과
Frida는 실행 중인 프로세스의 메모리에 자바스크립트를 주입하여 앱 내의 측정 함수나 변수및 반환값 등을 가로채는 도구다. Frida Mode에서 이 스크립트를 올바르게 구성해야 하는 이유는 다음과 같다.

1. **Persistent Mode(지속 실행 모드) 통한 성능 극대화**: 소스코드가 없는 바이너리를 그냥 퍼징하면 매번 메인(main) 함수부터 프로세스를 새로 껐다 켜야 하므로 속도가 떨어진다. 스크립트로 타겟 함수 주소를 루프로 묶어 메모리 상에서 반복 실행시키면 오버헤드가 제거되어 속도가 급증한다.
2. **계측 필터링 및 오염 방지**: 불필요한 OS 라이브러리(libc 등) 연산 경로를 배제하고 취약점이 의심되는 `fuzz_me` 함수 진입점만 핀포인트로 계측하여 효율을 극대화한다.

```js
try {
    // 1. 타겟 함수의 심볼 주소 찾기
    const pStartAddr = DebugSymbol.fromName("fuzz_me").address;
    
    if (pStartAddr) {
        // 2. AFL++가 퍼징을 시작할 진입점 지정
        Afl.setEntryPoint(pStartAddr);
        // 3. Persistent Mode: 매번 프로세스를 재시작하지 않고 같은 함수를 반복 호출해 속도 향상
        Afl.setPersistentAddress(pStartAddr);
        // 4. 한 프로세스당 함수를 반복 호출할 횟수
        Afl.setPersistentCount(1000);
        
        console.log("[*] Frida Injection Success! Target: " + pStartAddr);
    } else {
        console.log("[-] Error: 'fuzz_me' symbol not found.");
    }
} catch (e) {
    console.log("[-] Frida runtime error: " + e.message);
}

// Frida 초기화 완료 신호 - 반드시 호출해야 퍼징이 시작됨
Afl.done();
```

### 소스코드 없이 함수 주소 찾기
실습에선 내가 작성한 함수 이름을 알고 있기에 바로 스크립트에 어떤 함수명을 넣을지 알수 있었지만 실제로 퍼징을 수행할때는 소스코드 없이 수행을 하기때문에 리버싱도구로 바이너리를 열어서 fread, fgets, read같이 파일이나 네트워크 입력을 받는 함수를 찾고 이 데이터를 파싱하거나 복잡한 연산을 수행하는 하위 함수(sub_xxxxxx)를 찾고 이 함수를 타겟으로 주소 오프셋을 명시한다.

### AFL++ Frida 퍼징 실행 및 계측 분석
Frida Mode를 활성화하기 위해 `-O` 플래그를 추가한다. 가상환경 세션 꼬임 및 화면 깨짐을 유발할 수 있는 디버그용 출력 옵션들을 명시적으로 정리(`unset`)한 뒤 구동한다.

```sh
# 구형 세션 플래그 정리 및 환경변수 주입
unset AFL_DEBUG
unset AFL_DEBUG_CHILD
unset AFL_FRIDA_VERBOSE
export AFL_FRIDA_JS_SCRIPT=hook.js
export AFL_NO_FORKSRV=1 # 포크서버와 가상 링커 간의 통신 충돌 방지

../AFLplusplus/afl-fuzz -O -m none -i in -o out -- ./target_bin @@
# 사람마다 afl-fuzz가 있는 경로가 다를수 있어 이를 고려해서 실행해야함
```

#### 퍼징 결과
* **saved crashes : 1**  
  가동 후 약 2분 만에 카운터가 빨간색으로 점멸하며 취약점을 포착했다. 소스코드를 모르는 상태에서 오직 실행 경로 피드백 지도만을 따라 변이하다가 기어코 정답 레이아웃인 `FU` 조합을 스스로 맞춰 널 포인터를 터뜨렸다는 증거다.
* **exec speed : 898.0/sec**  
  바이너리를 dynamic binary instrumentation(DBI)하는 고유 제약 속에서도 초당 900회에 달하는 가공할 타격 페이스를 보여준다. 자바스크립트 Persistent Mode 세팅이 먹혀든 덕분이다.
* **stability : 100.00%**  
  무작위 변이 공격 중에도 타겟 바이너리가 퍼저의 제어권을 이탈해 조기 종료(Silent Death)되지 않고 정상 레이아웃 하네스 내에서 구동됨을 의미한다.

_crashes 디렉터리에 박제된 최초의 취약점 파일 확인_

디렉터리 내부에 명백한 메모리 결함 시그널 마크가 새겨진 치명적 변이 입력 파일(`id:000000...`)이 정상 생성되었다. 파일 이름에 부여된 메타데이터의 의미는 다음과 같다.

* **`id:000000`**: 퍼징 세션 전체를 통틀어 탐지해 낸 0번째 고유 독점 크래시 데이터.
* **`sig:11`**: 리눅스 커널이 발행한 시그널 11, 즉 **세그멘테이션 폴트(SIGSEGV)** 예외 발동 증거.
* **`op:havoc`**: 무작위 파괴 변이 기법인 havoc 연산 가공 단계를 거치다가 분기 장벽을 관통함.

해당 바이너리 입력값을 헥사 뷰어나 출력 명령어로 교차 검증해 보면, 내부 로직을 모르는 퍼징 엔진이 오직 비트맵 지도 피드백에만 의존해 전방 버퍼에 **`FU`** 문자열을 밀어 넣는 최적의 페이로드를 자가 생성해 냈음을 최종 확인할 수 있다.
