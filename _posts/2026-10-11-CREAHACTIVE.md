## OS 커맨드 인젝션

### What is OS Command Injection?

OS 커맨드 인젝션은 웹 애플리케이션이 사용자 입력을 운영체제 명령어에 안전하지 않게 포함해 실행할 때 발생한다. 공격자는 입력을 조작해 애플리케이션이 의도한 작업 외의 시스템 명령어까지 서버에서 실행하게 할 수 있다. 셸 인젝션(shell injection)이라고도 한다.

SQL 인젝션이 데이터베이스에 전달되는 SQL 문장을 공격한다면, OS 커맨드 인젝션은 서버 운영체제의 명령어 실행 과정을 공격한다. 따라서 공격 대상과 잠재적 영향이 다르다. 크리핵티브는 OS 커맨드 인젝션을 사용자 입력을 통해 시스템 명령어를 실행하는 취약점으로 설명하며, 가능하면 시스템 명령어를 사용하는 기능 자체를 구현하지 말 것을 권한다.

웹 애플리케이션은 사용자 입력을 바탕으로 시스템 명령어를 실행하는 기능을 제공할 수 있다. 예를 들어 서버가 네트워크 상태나 파일 정보를 확인하려고 운영체제 명령어를 호출하는 경우다. 이때 입력을 명령어 문자열에 안전하지 않게 결합하면 사용자가 의도한 값이 명령어의 일부로 해석될 수 있다.

### Impact

명령어가 서버에서 실행되면 공격자는 애플리케이션이 실행되는 계정의 권한 범위에서 파일을 읽거나 변경하고, 애플리케이션과 서버의 동작을 방해할 수 있다. 서버가 접근 가능한 내부 시스템이나 다른 자원까지 영향을 받을 가능성도 있다. 크리핵티브는 서버의 명령어 실행 권한을 통해 서비스 중단, 중요 정보 접근, 내부 시스템으로의 접근 시도 등이 가능할 수 있다고 설명한다. 실제 피해 범위는 애플리케이션 실행 계정의 권한과 서버 환경에 따라 달라진다.

명령어 실행 결과가 HTTP 응답에 표시되지 않는 **Blind OS Command Injection**도 있다. 응답에 출력이 보이지 않아도 명령어가 실행됐을 가능성이 있으므로, 취약점 확인에는 응답 외의 검증 방법이 필요하다. [PortSwigger: OS Command Injection](https://portswigger.net/web-security/os-command-injection)

### Mitigation

가장 효과적인 방어는 가능한 경우 셸 명령어 호출을 없애고, 애플리케이션이나 플랫폼이 제공하는 안전한 API로 같은 기능을 구현하는 것이다.

셸 호출이 불가피하다면 다음 원칙을 적용한다.

- 사용자 입력을 명령어 문자열에 이어 붙이지 않는다.
- 셸을 거치지 않고 실행 파일과 인자를 분리해 전달하는 API를 사용한다.
- 입력값은 필요한 형식과 허용 목록에 따라 엄격하게 검증한다. 예를 들어 숫자 필드에는 숫자만 허용한다.
- 셸 메타문자를 치환하거나 이스케이프하는 방식에만 의존하지 않는다. 이러한 처리는 누락이나 우회에 취약할 수 있다.
- 애플리케이션은 필요한 최소 권한으로 실행한다.

[PortSwigger: OS Command Injection 방어](https://portswigger.net/web-security/os-command-injection#how-to-prevent-os-command-injection-attacks)

## XSS

### What is XSS?

XSS(Cross-Site Scripting)는 취약한 웹 애플리케이션이 공격자의 스크립트를 사용자에게 전달하고, 피해자의 브라우저가 이를 실행하게 만드는 취약점이다. 스크립트는 취약한 사이트의 출처(origin)에서 실행되므로, 브라우저의 동일 출처 정책(SOP)이 의도한 사이트 간 분리를 악용할 수 있다. 공격자는 피해자가 애플리케이션에서 수행할 수 있는 작업을 대신 수행하거나 피해자가 접근할 수 있는 데이터에 접근할 수 있다. 피해자가 관리자라면 애플리케이션의 기능과 데이터가 크게 위협받을 수 있다.

> XSS는 취약한 웹 사이트가 공격자가 제어하는 스크립트를 포함한 응답을 반환하게 만드는 방식으로 동작한다. 브라우저가 그 스크립트를 실행하면, 공격자는 취약한 사이트와 사용자 간의 상호작용을 악용할 수 있다.

XSS는 다음과 같은 피해로 이어질 수 있다.

- **사용자 사칭 및 무단 작업 수행:** 피해자의 권한으로 애플리케이션에서 가능한 작업을 수행한다.
- **정보 열람 및 변경:** 피해자가 볼 수 있는 정보를 읽거나 변경한다.
- **피싱 및 자격 증명 탈취:** 가짜 로그인 화면 등을 표시해 사용자가 정보를 입력하도록 유도할 수 있다.
- **사이트 변조 및 악성 기능 삽입:** 사용자에게 보이는 페이지를 바꾸거나 악성 기능을 페이지에 삽입할 수 있다.
- **다른 사용자 공격:** 피해자 계정으로 다른 사용자와 상호작용해 공격을 확산할 수 있다.

XSS가 곧바로 악성 프로그램을 사용자의 기기에 다운로드하고 실행한다는 뜻은 아니다. 브라우저나 다른 취약점을 추가로 악용하는 경우와 XSS 자체로 가능한 행위는 구분해야 한다. CSRF 역시 XSS의 유형이 아니라 별개의 공격이다. 다만 XSS가 발생하면 피해자의 브라우저에서 공격자가 의도한 요청을 보내게 할 수 있다.

XSS에는 세 가지 주요 유형이 있다: **반사형(Reflected), 저장형(Stored), DOM 기반(DOM-based)**.

### Reflected XSS

반사형 XSS는 웹 애플리케이션이 HTTP 요청으로 받은 데이터를 안전하지 않은 방식으로 **즉시 응답에 포함할 때** 발생한다.

예를 들어 사용자가 메모 내용을 URL 매개변수로 전달하고, 애플리케이션이 그 내용을 페이지에 표시한다고 하자.

```text
https://example.com/memo?m=Well+That%27s+it.
```

응답 페이지:

```html
<p>memo: Well That's it.</p>
```

애플리케이션이 입력값을 안전하게 처리하지 않는다면, 공격자는 스크립트가 포함된 요청을 만들 수 있다.

```text
https://example.com/memo?m=<script>/* PAYLOAD */</script>
```

응답 페이지:

```html
<p>memo: <script>/* PAYLOAD */</script></p>
```

피해자가 공격자가 만든 링크를 열면 스크립트가 피해자의 브라우저에서 해당 애플리케이션의 세션 컨텍스트로 실행될 수 있다. 따라서 공격자는 피해자의 권한으로 작업을 수행하거나 피해자가 볼 수 있는 정보에 접근할 수 있다. 반사형 XSS는 보통 피해자가 공격자의 링크나 요청을 열도록 유도해야 한다. [PortSwigger: Reflected XSS](https://portswigger.net/web-security/cross-site-scripting/reflected)

#### Reflected XSS 분석 시 확인할 점

입력값이 검색 결과 화면에 표시된다는 사실만으로는 반사형 XSS라고 단정할 수 없다. 서버가 입력값을 응답에 포함했을 수도 있고, 브라우저의 JavaScript가 입력값을 읽어 화면을 만들었을 수도 있기 때문이다.

크리핵티브의 실습은 검색어를 입력한 뒤 응답 내용을 확인해 이 차이를 살펴본다. 입력값이 응답에 포함되어 서버 측에서 동적 페이지를 구성했다면 반사형 XSS 가능성을 확인한다. 응답에는 입력값이 없는데 화면에는 표시된다면, 클라이언트 측 JavaScript가 DOM을 구성하는지 살펴볼 필요가 있다.

또한 테스트용 스크립트가 실행되었는지 확인할 때 쿠키 값을 경고창에 표시하는 방식만 사용하면 안 된다. 쿠키에 `HttpOnly`가 설정되어 있으면 JavaScript에서 쿠키를 읽을 수 없기 때문이다. 쿠키가 표시되지 않더라도 스크립트 실행 자체는 성공했을 수 있으므로, 쿠키 접근 여부와 XSS 발생 여부를 구분해야 한다.

### Stored XSS

저장형 XSS는 애플리케이션이 신뢰할 수 없는 데이터를 받은 뒤 저장하고, 이후 그 데이터를 안전하지 않은 방식으로 HTTP 응답에 포함할 때 발생한다. 영구형(Persistent) XSS라고도 한다.

데이터는 여러 경로를 통해 들어올 수 있다.

- HTTP 요청: 블로그 댓글, 채팅 메시지, 상품 주문의 연락처 등
- 이메일: 웹 메일 서비스가 받은 메시지를 표시하는 경우
- 외부 게시물: 마케팅 애플리케이션이 소셜 미디어 게시물을 가져와 표시하는 경우
- 네트워크 데이터: 모니터링 애플리케이션이 패킷 정보를 화면에 표시하는 경우

예를 들어 댓글이 다음과 같은 요청으로 제출된다고 하자.

```http
POST /post/comment HTTP/1.1
Host: vulnerable-website.com
Content-Length: 100

postId=3&comment=This+post+was+extremely+helpful.&name=Carlos+Montoya&email=carlos%40normal-user.net
```

댓글이 저장된 뒤 블로그 페이지는 방문자에게 다음과 같은 응답을 반환할 수 있다.

```html
<p>This post was extremely helpful.</p>
```

애플리케이션이 댓글을 안전하게 처리하지 않는다면, 공격자가 스크립트가 포함된 댓글을 제출할 수 있다.

```text
comment=<script>/* PAYLOAD */</script>
```

해당 댓글이 페이지에 그대로 포함되면 응답은 다음과 같은 형태가 된다.

```html
<p><script>/* PAYLOAD */</script></p>
```

이 페이지를 방문하는 사용자의 브라우저에서 스크립트가 실행될 수 있다. 저장형 XSS는 공격자가 애플리케이션 안에 악성 입력을 저장해 두므로, 피해자가 공격자의 외부 링크를 열도록 유도하지 않아도 공격이 전달될 수 있다. [PortSwigger: Stored XSS](https://portswigger.net/web-security/cross-site-scripting/stored)

### DOM-based XSS

DOM 기반 XSS는 서버가 응답에 악성 입력을 직접 넣지 않더라도, 브라우저에서 실행되는 JavaScript가 신뢰할 수 없는 입력을 안전하지 않게 처리해 DOM에 삽입할 때 발생한다. DOM은 브라우저가 HTML 문서를 표현하고 조작하는 구조다.

이 취약점을 이해할 때는 입력이 시작되는 **source**와 입력이 전달되어 사용되는 **sink**를 살펴본다.

- **Source:** 공격자가 제어할 수 있는 데이터가 들어오는 지점이다. URL의 `location.search`나 `location.hash` 등이 이에 해당한다.
- **Sink:** 전달된 값을 HTML이나 코드로 해석하거나 실행할 수 있는 지점이다. `innerHTML`, `document.write`, `eval()` 등이 위험한 sink의 예다.

예를 들어 페이지의 JavaScript가 URL에서 `keyword` 값을 읽고 `innerHTML`로 검색 결과 영역에 넣는다고 하자.

```javascript
const keyword = new URLSearchParams(location.search).get("keyword");
document.getElementById("searchResult").innerHTML =
  "검색어: " + keyword;
```

`innerHTML`은 값을 일반 텍스트가 아니라 HTML로 해석한다. 따라서 신뢰할 수 없는 입력이 이 sink까지 안전한 처리 없이 전달되면 브라우저가 입력을 HTML로 해석해 스크립트 실행으로 이어질 수 있다. 크리핵티브 6장의 실습은 URL에서 `keyword`를 읽고, 문자열에 연결한 뒤 `innerHTML`을 통해 검색 결과 영역에 넣는 흐름을 보여 준다. 즉, 취약점의 핵심은 입력값이 클라이언트 코드에서 위험한 sink까지 전달되는 경로다. [PortSwigger: DOM-based XSS](https://portswigger.net/web-security/cross-site-scripting/dom-based)

#### Reflected XSS와의 차이

반사형 XSS는 사용자 입력이 서버에 전달되고, 서버가 그 값을 안전하지 않게 즉시 HTTP 응답에 포함할 때 발생한다. DOM 기반 XSS는 클라이언트 측 JavaScript가 입력을 처리해 페이지를 변경하는 과정에서 발생할 수 있다. 따라서 DOM 기반 XSS는 응답 원문에 입력값이 보이지 않아도 취약할 수 있다.

DOM 기반 XSS를 확인할 때는 개발자 도구로 실행 후 DOM을 살펴보고, 입력값이 어떤 JavaScript 코드와 sink를 거치는지 확인한다. 페이지 소스만 보면 JavaScript 실행 뒤 변경된 DOM을 놓칠 수 있다. 입력값이 DOM에 나타나지 않는 경우에는 디버거를 사용해 JavaScript 실행 흐름에서 source가 sink로 전달되는지도 확인한다.

[PortSwigger: DOM 기반 취약점의 Source와 Sink](https://portswigger.net/web-security/dom-based)

### XSS Context

XSS 테스트에서 **컨텍스트(context)**란 사용자 입력이 응답이나 DOM의 어느 위치에 들어가는지, 그리고 그 전에 어떤 검증이나 변환을 거치는지를 뜻한다. 같은 입력도 삽입 위치에 따라 브라우저가 해석하는 방식이 다르므로 컨텍스트를 파악해야 한다.

대표적인 컨텍스트는 다음과 같다.

- **HTML 본문:** 입력값이 HTML 태그 사이에 들어가는 경우
- **HTML 속성:** 입력값이 `value`, `title` 같은 속성 값에 들어가는 경우. 속성 값이 따옴표로 둘러싸였는지도 살펴야 한다.
- **JavaScript:** 입력값이 `<script>` 내부 코드나 이벤트 핸들러 속성의 JavaScript 문자열에 들어가는 경우
- **URL:** 입력값이 링크의 `href` 같은 URL 속성에 들어가는 경우. 허용되는 프로토콜도 확인해야 한다.
- **DOM:** 클라이언트 측 코드가 URL이나 다른 입력을 읽어 페이지의 DOM에 넣는 경우

따라서 입력값이 응답에 보이는지만 확인해서는 충분하지 않다. 값이 HTML이나 JavaScript로 해석되는지, 일반 텍스트로 처리되는지, 애플리케이션이 어떤 변환을 적용하는지 함께 살펴야 한다. [PortSwigger: XSS 컨텍스트](https://portswigger.net/web-security/cross-site-scripting/contexts)

### Impact of XSS

XSS로 실행되는 스크립트가 피해자의 브라우저에서 애플리케이션의 권한을 얻으면, 피해자가 할 수 있는 작업을 대신 수행하거나 피해자가 볼 수 있는 정보를 읽고 변경할 수 있다. 피해자의 계정으로 다른 사용자와 상호작용하거나 가짜 화면을 표시하는 데 악용될 수도 있다.

실제 영향은 애플리케이션의 기능과 보유 데이터, 공격 대상 사용자의 권한에 따라 달라진다. 공개 정보만 제공하는 사이트에서는 영향이 제한적일 수 있지만, 금융·이메일·의료 정보 등을 처리하는 서비스에서는 피해가 심각해질 수 있다. 관리자 계정이 공격받으면 애플리케이션의 기능과 사용자 데이터 전반이 위협받을 수 있다.

반사형 XSS는 보통 피해자가 공격자가 만든 링크나 요청을 열도록 유도해야 한다. 저장형 XSS는 악성 입력이 애플리케이션에 저장되어 해당 페이지를 방문하는 사용자에게 전달될 수 있으므로 더 많은 사용자를 공격할 가능성이 있다. [PortSwigger: XSS 영향](https://portswigger.net/web-security/cross-site-scripting)

### XSS Mitigation

XSS 방어의 핵심은 **출력 위치에 맞는 인코딩**과 **안전한 DOM 처리**다.

1. **출력 시점에 컨텍스트별 인코딩을 적용한다.** HTML 본문, HTML 속성, JavaScript 문자열, URL 등 각 위치에 맞는 인코딩 방법을 사용한다. 한 종류의 인코딩을 모든 컨텍스트에 공통으로 적용해서는 안 된다.
2. **입력값은 기대하는 형식에 맞게 검증한다.** 숫자를 기대하는 필드는 숫자인지 확인하고, URL은 `https` 등 허용된 프로토콜만 받는 식으로 허용 목록을 기준으로 검증한다. 입력 검증만으로 출력 인코딩을 대체할 수는 없다.
3. **클라이언트 측 코드에서 위험한 sink를 피한다.** 사용자 입력을 HTML로 해석하는 `innerHTML`이나 `document.write`에 직접 넣지 않는다. 일반 텍스트를 표시할 때는 HTML로 해석하지 않는 `textContent` 같은 방법을 사용한다.
4. **HTML 입력이 꼭 필요하다면 검증된 HTML 정화기를 사용한다.** 크리핵티브는 HTML 태그 사용이 필요 없는 입력에는 HTML 엔티티 인코딩을, 서식 있는 게시글처럼 HTML 사용이 필요한 경우에는 보안 라이브러리를 사용하는 방안을 소개한다. 태그와 속성을 직접 블랙리스트로 제거하는 방식은 브라우저 파싱 차이와 우회 가능성 때문에 안전하게 구현하기 어렵다. 정화 라이브러리를 사용한다면 보안 업데이트를 적용한다.
5. **입력 저장 전후의 처리 지점을 확인한다.** 크리핵티브의 시큐어 코딩 실습에서는 게시글의 제목과 내용이 검증 없이 저장되고 출력되는 부분을 찾아 대응한다. 다만 인코딩은 실제로 출력되는 컨텍스트에 맞춰 적용해야 하며, 입력 시점의 처리만으로 모든 출력 경로를 안전하게 만들 수 있는 것은 아니다.
6. **CSP와 응답 헤더를 추가 방어층으로 사용한다.** Content Security Policy(CSP)는 스크립트 실행과 리소스 로드를 제한해 남아 있는 취약점의 피해를 줄일 수 있지만, 출력 인코딩이나 안전한 DOM 처리를 대신하지는 않는다. HTML이 아닌 응답에는 의도한 형식으로 해석되도록 올바른 `Content-Type`과 `X-Content-Type-Options` 헤더도 설정한다.
7. **쿠키에 `HttpOnly`를 적용한다.** JavaScript를 통한 쿠키 읽기를 제한해 쿠키 탈취 위험을 낮출 수 있다. 크리핵티브의 실습도 `HttpOnly` 설정에 따라 JavaScript에서 쿠키가 읽히지 않는 것을 보여 준다. 다만 `HttpOnly`는 XSS 자체를 막거나 피해자의 브라우저에서 악성 스크립트가 다른 작업을 하는 것을 방지하지는 않으므로, 출력 인코딩과 안전한 DOM 처리를 함께 적용해야 한다.
