## Intro
GAST(Gachon Dynamic Application Security Testing)는  Typescript기반 DAST 엔진으로, SQLi, XSS등의 보안 취약점을 동적으로 분석해준다.
해당 글은 GAST 엔진의 전체적인 구조, 흐름 등을 분석하여 정리한 글이다. 스터디 목적의 글이면서 개발이 주제이기 떄문에 카테고리는 개발로 분류했다.

### 목차
- 전체 구조
- 동기/비동기 처리
- 테스트 웹
- API및 데이터 흐름

## 전체 아키텍쳐
![Big-Architecture](/assets/img/posts/develop/GAST/01-big-picture.png)
> GAST동작의 큰 흐름

진입점은 웹 대시보드, CLI, 스크립트 세 가지이지만 모두 `scan()` 함수 하나를 호출한다. `scan()`은 인증, 정적 수집, (선택) 브라우저 수집, 헤더 검사, 입력별 능동 검사 순서로 각 모듈을 호출하는 지휘자이다.

- 모든 HTTP 요청은 `HttpClient`(`http.ts`) 한 곳을 거친다. 범위 확인, 쿠키, 요청 예산, 응답 기록이 여기서 처리된다.
- 예외는 Chromium(Playwright)이다. 브라우저는 별도 경로로 요청을 보내고 요청 수도 따로 센다.
- 검사 대상은 로컬 HTTP(`127.0.0.1`, `localhost`, `[::1]`)로 제한된다.

> 그림의 화살표는 호출과 데이터 전달을 뜻하며 import 관계를 전부 그린 것은 아니다. 그림에는 `rules.ts`가 XSS 실행 확인을 위해 `browser.ts`의 `verifyXss`를 직접 호출하는 경로가 빠져 있다.

의존 방향은 단순하다.

- `types.ts`와 `scope.ts`는 다른 모듈에 의존하지 않는 기반이다.
- `http.ts`는 `scope.ts`로 범위를 확인하고, `crawler.ts`는 `html.ts`와 `scope.ts`를 쓴다.
- `rules.ts`는 `html.ts`로 DOM을 분석하고, XSS 실행 확인이 필요할 때 `browser.ts`의 `verifyXss`를 호출한다.
- `scanner.ts`가 `http`, `crawler`, `browser`, `rules`를 모아 순서를 정하고, `cli.ts`와 `studio.ts`가 `scanner.ts`를 호출한다.
- `lab.ts`는 검사 대상 서버라서 엔진 모듈과 직접 연결되지 않고, `studio.ts`를 직접 실행할 때 함께 띄운다.

> 읽는 순서: `types` → `scope` → `http` → `html` → `crawler` → `rules` → `scanner` → `report` → `cli` → `studio`와 `web` → `browser` → `lab`. 데이터 모양(`types.ts`)을 먼저 보면 나머지 코드가 훨씬 쉽게 읽힌다.

### Pipeline

![Scan-Steps](/assets/img/posts/develop/GAST/02-scan-steps.png)
> scan() 한 번이 지나가는 단계

`scan(target, options)`는 아래 순서로 실행되고, 단계가 바뀔 때마다 `phase` 값이 진행 이벤트로 대시보드와 CLI에 전달된다.

| 단계 | 하는 일 | 담당 | 새 HTTP 요청 |
| --- | --- | --- | --- |
| 0. 검증 | 정수 한도, 규칙 이름, 제외 경로를 확인하고 잘못되면 요청 전에 예외를 던진다 | `validateOptions` | 없음 |
| 1. authentication | 로그인 POST 후 검증 GET의 상태 200과 성공 문자열을 확인한다 | `HttpClient.login` | 2회 |
| 2. crawl | 시작 주소부터 BFS로 링크를 따라가며 입력 지점(`InputPoint`)을 수집한다 | `crawl`, `parsePage` | 페이지당 1회 |
| 3. browser | Chromium으로 DOM 링크를 따라가고 `data-gast-explore` 버튼을 눌러, 발생한 GET 요청의 쿼리를 입력 지점에 추가한다 | `browserCrawl` | 브라우저 별도 예산 |
| 4. passive | 이미 받은 200 HTML 응답에서 보안 헤더 존재 여부만 확인한다 | `passive` | 없음 |
| 5. active | 입력 지점마다 정상 응답 2회를 받고, 변형 가능한 입력을 하나씩 검사한다 | `send`, `testInput` | 규칙별 |
| 6. complete | `ScanResult`를 조립해 반환한다 | `scan` | 없음 |

- `authentication`은 `auth` 옵션이 있을 때, `browser`는 `browser` 옵션이 켜졌을 때, `passive`는 `headers` 규칙이 켜졌을 때만 거친다. `ruleIds`를 빈 배열로 주면 탐색만 한다.
- 능동 검사에서 hidden 입력은 같이 전송하되 변형하지 않는다(`mutable=false`). 규칙이 돌려준 후보에는 `scanner.ts`가 `id`를 붙여 `findings`에 넣는다.
- 요청은 전부 순차(`await`를 하나씩)로 보낸다. 기준, 검사, 재검사의 순서가 곧 증거의 의미이고, 요청 예산을 정확히 세고 대상 서버에 부담을 주지 않기 위해서이다.
- 오류나 취소가 나도 `try/catch`로 잡아 지금까지 얻은 결과를 그대로 반환한다.

**오류가 나도 결과가 남는 구조 (`src/scanner.ts` L53, L85~L114 발췌)**

```ts
  try {
    // ... authentication · crawl · browser · passive 단계 (생략)
    phase = 'active';
    for (const point of discovery.points) {
      options.signal?.throwIfAborted();
      emit(`기준 응답 반복 측정 ${point.method} ${point.url}`);
      try {
        // 정상 응답을 두 번 받아 시간에 따른 차이를 확인합니다. hidden 입력은 유지하고 mutable 입력만 검사합니다.
        const baselines = [await send(client, point), await send(client, point)];
        for (let index = 0; index < point.params.length; index++)
          if (point.mutable[index]) {
            for (const finding of await testInput(client, point, index, baselines, options, emit)) {
              findings.push({ id: findings.length + 1, ...finding });
              emit(`발견 ${finding.ruleId} · ${finding.parameter}`);
            }
          }
        // 취소나 치명적인 단계 실패도 현재까지 얻은 자료를 결과에 남깁니다. 일부 항목 실패는 내부 catch에서 계속 처리합니다.
      } catch (error) {
        if (options.signal?.aborted) throw error;
        discovery.errors.push({ url: point.url, message: (error as Error).message });
        if (client.count >= client.maxRequests) break;
      }
    }
  } catch (error) {
    cancelled = options.signal?.aborted ?? false;
    discovery.errors.push({
      url: target,
      message: cancelled ? '사용자가 검사를 취소했습니다.' : (error as Error).message,
    });
  }
  phase = 'complete';
  emit(cancelled ? '검사 취소' : discovery.errors.length ? '오류를 포함하여 종료' : '검사 종료');
```
{: file="src/scanner.ts" }

`catch`가 두 겹이고 역할이 다르다.

- **안쪽 `catch`(입력 지점 하나)**: 요청 실패나 타임아웃이 나면 `errors`에 기록하고 다음 입력 지점으로 넘어간다. 사용자가 취소한 경우(`signal.aborted`)는 다시 던져서 바깥으로 보내고, 요청 예산을 다 썼으면 `break`로 능동 검사를 끝낸다.
- **바깥 `catch`(검사 전체)**: 인증, 크롤, 브라우저 단계의 예외와 위에서 다시 던진 취소를 받아 `errors`에 한 줄 기록한다. 다시 던지지 않으므로 `scan()`은 실패(reject)하지 않고 `phase = 'complete'` 다음의 `return`까지 간다. 취소 여부는 에러 이름이 아니라 `signal.aborted`로 판단한다.
- **결과가 남는 이유**: `findings`, `events`, `client`(응답 기록 `history`), `discovery`가 모두 `try` 바깥에서 선언돼 있다. 예외로 빠져나와도 `findings.push`로 쌓아 둔 발견과 지금까지의 응답 기록이 그대로 `ScanResult`에 담긴다.
- **표시**: 오류가 하나라도 있으면 `summary.complete`가 `false`이고 마지막 이벤트가 "오류를 포함하여 종료"가 된다. 취소는 `summary.cancelled`가 `true`이고 CLI 종료 코드는 2이다.

코드 안의 주석은 이 두 겹을 한꺼번에 적어 둔 것이다. "치명적인 단계 실패"는 바깥 `catch`, "일부 항목 실패"는 안쪽 `catch`에서 처리한다.

> 예외로 끝나는 경우도 있다. `scan()` 맨 앞의 `validateOptions`와 `new HttpClient`는 `try` 바깥이라 잘못된 설정은 요청을 보내기 전에 예외로 끝난다. 또 `crawl()` 자체가 예외로 끝나면 `discovery`에는 아직 초기 빈 값이 들어 있으므로, 어느 단계에서 실패했는지에 따라 남는 결과의 양이 다르다.
{: .prompt-info }

> `summary.complete`는 오류, 취소, 한도 초과 없이 작업이 끝났다는 뜻일 뿐 취약점이 없다는 보증이 아니다.
{: .prompt-warning }

### Vulnerabillity Assessment

![Detection-Rules](/assets/img/posts/develop/GAST/03-detection-rules.png)
> 세 규칙 모두 기준 2회, 검사, 대조, 재검사 순서로 근거를 쌓는다

응답 하나가 달라 보인다고 바로 취약점으로 보고하지 않는다. 정상 응답(기준), 변형 입력(검사), 무해한 입력(대조), 같은 검사의 반복(재검사)을 모두 비교해서 "반복되고, 대조군에서는 나타나지 않는" 것만 후보로 올린다.

| 규칙 | 보내는 요청 | 후보가 되는 조건 | 위험도 / 신뢰도 |
| --- | --- | --- | --- |
| `sqli-error` | 값 뒤에 `'`를 붙인 요청 | DB 오류 문구가 나타남, 기준 응답 2개에는 없음, 대조 입력(`값+gastcontrol`)에는 없음, 같은 검사를 다시 보내면 다시 발생 | high / medium |
| `sqli-boolean` | 참 조건과 거짓 조건 쌍 (숫자라면 `AND 1=1`, `AND 1=2`) | 기준 응답이 안정적(유사도 0.98 이상, 상태 200)일 때만 시작. 참은 기준과 거의 같고(0.98 이상) 거짓은 다름(0.8 미만). 거짓, 참 순서로 다시 보내도 재현되고 무해한 대조 입력이 200 | high / medium |
| `xss-context` | 무해한 토큰으로 반사 문맥 확인, 문맥에 맞는 시험 입력, 재전송 | 응답 DOM에 `__gastProof('토큰')`을 가진 `svg`/`img` 이벤트 요소가 생김. `verifyXss` 옵션이면 실제 Chromium에서 콜백 실행까지 확인 | medium / 실행 확인 시 high |
| 헤더 (passive) | 없음 | CSP, X-Content-Type-Options 헤더가 없음 | low / high |

응답 비교에는 유사도를 쓴다. 본문을 DOM 텍스트로 바꾸고 긴 숫자와 hex 문자열을 `#`으로 치환해 잡음을 줄인 뒤, 문자 3-gram 집합의 Dice 계수(0~1)로 계산한다. 예를 들어 `abcd`와 `abce`의 3-gram은 {abc, bcd}와 {abc, bce}이므로 2×1 / (2+2) = 0.5이다.

XSS는 먼저 무해한 토큰이 HTML의 어느 위치에 반사되는지 찾고, 그 문맥에 맞는 시험 입력을 고른다.

| 반사 문맥 | 시험 입력 |
| --- | --- |
| 본문 (text) | `<svg onload="__gastProof('토큰')">` |
| 속성 (attribute) | `">` + 위 태그 + `<i data-x="` |
| 주석 (comment) | `-->` + 위 태그 + `<!--` |
| textarea, title | `</textarea>` 또는 `</title>` + 위 태그 |
| script | `';__gastProof('토큰');//` (정적으로 확정하기 어려워 실행이 확인될 때만 보고) |

> 위험도(severity)와 신뢰도(confidence)는 다른 값이다. 또 태그가 만들어진 것(구조 경고, `browserVerified: false`)과 브라우저에서 토큰 콜백이 실제로 실행된 것(`browserVerified: true`)은 구분한다. CSP에 막힌 `/xss/csp` 사례가 그 예이다. `browserVerified`가 없으면 해당 규칙에 적용되지 않는다는 뜻이다.
{: .prompt-info }

### Data Flow

![Data-Flow](/assets/img/posts/develop/GAST/04-data-flow.png)
> 주소 한 줄이 증거 보고서가 되기까지

전체 파이프라인은 `types.ts`에 정의된 데이터 타입이 이어지는 흐름으로 볼 수 있다.

| 타입 | 역할 | 핵심 필드 |
| --- | --- | --- |
| `InputPoint` | 검사할 입력 한 덩어리 | `url`, `method`, `params`(이름·값 쌍 배열), `mutable`(params와 같은 인덱스), `source`, `kind`(query, form, network) |
| `Exchange` | 요청·응답 한 쌍의 기록 | `id`, `request`, `status`, `headers`, `body`, `elapsedMs`, `bytes` |
| `Finding` | 발견 후보와 근거 | `ruleId`, `severity`, `confidence`, `payload`, `reason`, `baselineId`, `probeId`, `confirmationId`, `controlIds`, `browserVerified`, `comparison` |
| `ScanResult` | 최종 산출물 | `summary`, `pages`, `points`, `findings`, `errors`, `skipped`, `history`, `events` |

`Finding`은 응답 본문을 복사하지 않고 ID만 가진다. 보고서와 대시보드는 이 ID로 `history`에서 원문을 찾아 정상 응답과 검사 응답을 나란히 보여 준다.

```text
Finding.baselineId      → history 안의 정상(기준) 응답
Finding.probeId         → 첫 검사 응답
Finding.confirmationId  → 재검사 응답
Finding.controlIds[]    → 대조(정상 입력, 거짓 조건) 응답들
```

- `params`와 `mutable`은 같은 인덱스가 한 입력을 뜻한다. 이름이 같은 입력도 순서대로 보존하려고 객체 대신 배열을 쓴다.
- 입력 중복은 `pointKey`(메서드 + URL + 입력 이름 목록)로 판단한다. 값이 달라도 같은 구조는 하나로 합친다.
- 요청 시도 수(`count`)와 완료된 응답 기록(`history`)은 다르다. `count`는 `fetch` 직전에 증가하고 `history`는 응답을 다 읽은 뒤에 추가되므로, 타임아웃이나 취소로 실패한 요청은 예산에만 포함된다.
- 브라우저가 보낸 요청은 `history`에 들어가지 않고 `browserRequests`로 따로 집계한다.
- 결과의 `options`에는 로그인 비밀번호, `AbortSignal`, 콜백 함수를 저장하지 않는다.

### Restriction

**범위와 한도**

검사 대상은 인증 정보가 없는 로컬 HTTP 주소만 허용한다. 외부 주소는 `originOf`가 예외로 거부하고, 이후 모든 요청과 브라우저의 하위 요청도 같은 origin과 제외 경로를 다시 확인한다.

| 항목 | 값 |
| --- | --- |
| HTTP 요청 수 | 기본 400회 (대시보드 기본 800회) |
| 타임아웃 | 기본 4초 (대시보드 6초) |
| 요청 간 대기 | 15ms |
| 페이지 수 / 깊이 | 30 / 4 |
| 응답 크기 | 1 MiB 초과 시 오류 |
| 브라우저 요청 | 탐색 100회, 전체 200회, XSS 확인은 시도당 20회 |
| 브라우저 버튼 클릭 | `data-gast-explore` 속성이 있는 것만, 페이지당 최대 5개 |

설정값은 `validateOptions`가 범위를 검사한다(예: `maxPages` 1~100, `maxDepth` 0~10, `maxRequests` 1~3000).

**구현하지 않은 것**

- 범용 프록시와 TLS 중간자 기능
- OAuth, MFA, CSRF 토큰 갱신 등 임의 인증 시스템
- 저장형 XSS와 DOM XSS
- 시간 기반 SQLi (시간 차이는 기록만 하고 판정에 쓰지 않는다)
- JSON POST 능동 검사

**판별과 수집의 한계**

- 유사도 임계값(0.98, 0.8)은 고정된 실습 환경용 휴리스틱이라 실제 서비스에서는 오탐과 미탐이 가능하다.
- XSS는 반사 위치가 여러 곳이어도 첫 문맥만 대상으로 하고, 속성 탈출은 큰따옴표 중심이다.
- 로그인은 쿠키 기반이고 401을 받았을 때 한 번만 재로그인한다. 302로 로그인 화면에 보내거나 200 상태의 로그인 화면을 보여 주는 경우는 감지하지 못한다.
- 브라우저는 쿠키를 HTTP 클라이언트에서 한 방향으로 복사해 쓴다. localStorage 인증은 지원하지 않고 service worker는 차단한다.

**코드를 읽다가 확인한 구현상의 한계**

- `testInput`에는 `try/catch`가 없다. 그래서 한 입력 지점에서 요청 하나가 실패하면 예외가 `scanner.ts`의 지점 단위 `catch`로 올라가고, 그 지점의 남은 파라미터 검사는 건너뛴다.
- `openBrowser`는 Chromium을 띄운 뒤 컨텍스트를 만들고 쿠키를 복사하는데, 이 호출이 호출하는 쪽의 `try` 바깥에 있다. 컨텍스트 생성이 실패하면 `finally`의 `browser.close()`에 닿지 못한다. 저장소의 `CODE_REVIEW.md`도 이 한계를 후속 개선 대상으로 적어 두었다.

> 평가는 `lab.ts`의 고정된 11개 사례로 한다. 개발자 의도에 맞춰 만든 사례라서 높은 수치가 나와도 외부 사이트의 정확도로 일반화할 수 없다. ZAP과의 비교는 코드가 준비돼 있지만 실측은 미수행 상태이다.
{: .prompt-warning }

### Excution - (CLI / scripts / Dashboard)

**실행 환경**

Node.js 24 이상이 필요하다. `node:sqlite`와 `.ts` 파일 직접 실행을 쓰기 때문이며 빌드 단계는 없다. 의존성은 `parse5`(HTML 파서), `playwright`(Chromium 제어), `tough-cookie`(쿠키 보관) 세 개이다.

```bash
pnpm install
pnpm exec playwright install chromium   # 브라우저 탐색, XSS 실행 확인에 필요
pnpm studio                             # 실습실(3000)과 대시보드(3001)를 함께 실행
```

npm을 쓴다면 `npm install`, `npx playwright install chromium`, `npm run studio`를 사용한다. `tsc`는 타입 검사 전용(`pnpm check`)이다. Node는 타입만 지우고 실행하므로 실행이 된다고 타입이 맞는 것은 아니다.

**CLI (`src/cli.ts`)**

```bash
node src/cli.ts <URL> [--config=파일.json] [--browser] [--verify-xss] [--allow-post] [--out=폴더]
node src/cli.ts http://127.0.0.1:3000 --config=configs/presentation.json
```

- 설정 JSON을 먼저 읽고, `--browser`, `--verify-xss`, `--allow-post`는 해당 옵션을 켠다. 기본 출력 폴더는 `reports/latest`이다.
- `Ctrl+C`는 `AbortController`로 연결되어 검사를 취소하고, 부분 결과로 보고서를 저장한다.
- 종료 코드는 정상 0, 미완료(`summary.complete`가 false) 2, 설정 오류 등 예외 1이다.

**대시보드 (`src/studio.ts`)**

`http://127.0.0.1:3001`에서 열고, 실습실은 `http://127.0.0.1:3000`에서 같이 실행된다. 화면은 `web/`의 `index.html`, `app.js`, `style.css`이고 서버가 아래 API를 제공한다. 세부 흐름은 별도 글에서 다룬다.

| 메서드와 경로 | 동작 |
| --- | --- |
| `GET /api/bootstrap` | 쓰기 요청용 토큰과 최근 실행 목록 |
| `POST /api/scans` | 검사 시작. 접수만 하고 `202`와 `id`를 바로 응답하며 검사는 뒤에서 진행한다. 이미 실행 중이면 `409` |
| `GET /api/scans/:id` | 상태(`running`, `done`, `failed`), 진행 이벤트, 결과 |
| `POST /api/scans/:id/cancel` | 취소 요청 |
| `POST /api/scans/:id/review` | 수동 판정 저장 (`confirmed`, `false-positive`, `needs-review`) |
| `GET /api/scans/:id/report.html` | 보고서 보기. `report.json`, `report.sarif`도 같은 경로 형식 |

- 화면은 650ms마다 `GET /api/scans/:id`를 폴링해 진행 상황을 그린다.
- 쓰기 요청(POST)은 Host, Origin, `X-GAST-Token`, Content-Type을 모두 검사하고, 검사는 동시에 한 개만 실행한다. 실행 이력은 서버 메모리의 최근 20개이다.
- 수동 판정은 `reports/runs/<id>/reviews/<findingId>.json`에 따로 저장하고 원래 `Finding`을 덮어쓰지 않는다.
- 화면은 검사 결과를 `textContent`로만 출력해서, 결과에 들어 있는 공격 문자열이 대시보드에서 실행되지 않는다.

**스크립트 (`scripts/`)**

| 파일 | 설명 |
| --- | --- |
| `demo.ts` | 임시 포트로 실습실을 띄우고 브라우저 없이 전체 검사(POST 허용, 요청 800회)를 실행해 `reports/latest`에 저장 |

### Test Server

`lab.ts`는 포트 3000에서 실행되는 실습용 대상 서버이다. 메모리 SQLite(`node:sqlite`)에 `products` 테이블을 만들고, **취약한 경로와 안전한 대조 경로를 나란히** 제공한다. 이 정답표 덕분에 "탐지했는가"뿐 아니라 "안전한 곳을 취약하다고 하지 않았는가"까지 확인할 수 있다.

| 경로 | 성격 |
| --- | --- |
| `/sql/error?q=` | 문자열 연결 SQL, DB 오류가 그대로 노출 (취약) |
| `/sql/boolean?id=` | 숫자 연결 SQL, 오류는 감추고 참/거짓에 따라 응답이 달라짐 (취약) |
| `/sql/safe?q=` | 매개변수 바인딩 (안전) |
| `/xss/text`, `/xss/attribute`, `/xss/comment`, `/xss/textarea` | 문맥별로 입력을 이스케이프 없이 출력 (취약) |
| `/xss/safe` | HTML 이스케이프 (안전) |
| `/xss/csp` | 취약한 출력에 스크립트 실행을 막는 CSP를 더함 (구조 경고만, 실행은 안 됨) |
| `/noise` | 어떤 입력에도 `SQLITE_ERROR` 안내문이 항상 나옴 (오탐 유도) |
| `/forms`, `/submit` | 숨김, disabled, checkbox, textarea, select가 섞인 POST 폼 |
| `/spa`, `/api/product` | 버튼 클릭 시 `fetch`로 GET 요청 (브라우저 탐색 시험) |
| `/redirect` | 같은 origin 302 리다이렉트 |
| `/auth/login`, `/auth/status`, `/private` | 쿠키 세션 로그인 (README에 공개된 실습 계정 `student` / `gast-demo`) |

SQL 세 경로의 차이가 SQL Injection 이해의 핵심이다.

```ts
// 안전: 값을 매개변수로 바인딩
db.prepare('SELECT name,description FROM products WHERE name = ?').all(q);
// 취약: 숫자 자리에 문자열 연결 (1 AND 1=2 가 SQL 문법으로 해석됨)
db.prepare(`SELECT name,description FROM products WHERE id = ${id}`).all();
// 취약: 따옴표 안에 문자열 연결 (camera' 가 따옴표를 닫아 문법 오류)
db.prepare(`SELECT name,description FROM products WHERE name = '${q}'`).all();
```

`cases` 배열에 정의된 11개 사례가 `benchmark.ts`의 정답표이다. `/sql/safe`가 규칙 두 개(`sqli-error`, `sqli-boolean`)에 모두 걸려 있어서 경로는 10개이지만 사례는 11개로 센다.

| 구분 | 경로 | 정답 |
| --- | --- | --- |
| SQLi 오류 기반 | `/sql/error` | 취약 |
| SQLi 참거짓 기반 | `/sql/boolean` | 취약 |
| SQLi 안전 (규칙 2개) | `/sql/safe` | 안전 |
| XSS 4문맥 | `/xss/text`, `/xss/attribute`, `/xss/comment`, `/xss/textarea` | 취약 |
| XSS 이스케이프 | `/xss/safe` | 안전 |
| XSS + CSP | `/xss/csp` | 실행 기준으로는 안전 |
| 오탐 유도 | `/noise` | 안전 |

> `lab.ts`는 학습용으로 일부러 취약하게 만든 코드이다. 문자열 연결 SQL이나 이스케이프하지 않는 출력 패턴을 실제 제품 코드에 가져다 쓰면 안 된다. 자동 테스트와 대시보드의 상세 동작은 다음 글에서 다룬다.
