## Concept
`DOM based XSS`는 서버가 응답하는 HTML 자체에는 악성 스크립트가 삽입되지 않지만, 클라이언트 사이드 자바스크립트가 사용자 제어 가능한 값(URL, 프래그먼트, `document.referrer` 등)을 검증 없이 DOM에 반영(innerHTML, `document.write`, `eval` 등)할 때 발생하는 취약점이다.

일반적인 Reflected/Stored XSS는 서버가 페이로드를 응답 본문에 그대로 포함시키는 반면, DOM based XSS는 **서버 응답에는 문제가 없고 오직 브라우저에서 실행되는 JS 코드의 흐름**에서 문제가 발생한다는 점이 핵심 차이다. 그래서 분석할 때도 서버 로직보다 클라이언트 JS의 **Source(사용자가 제어 가능한 입력 지점)** 와 **Sink(그 값이 위험하게 사용되는 지점)** 를 먼저 특정해야 한다.

이를 막기 위헤 **CSP(Content Security Policy)의 nonce 기반 스크립트 화이트리스팅**를 사용할수 있다, 단순히 `<script>` 태그를 주입하는 것만으로는 실행이 되지 않고 **스크립트 가젯(Script Gadget)** 기법으로 공격자가 스크립트 태그를 주입해도 실행되지 않게 하는 것이다. 이 외에도 sanitizer나 WAF같은 방어기법이 존재한다.

## 서비스 분석
### Source & Sink
```js
window.addEventListener("load", function() {
  var name_elem = document.getElementById("name"); //Source
  name_elem.innerHTML = `${location.hash.slice(1)} is my name !`; //Sink
});
```
{: file="vuln.html"}

`id`가 `name`인 엘리먼트를 가져온 뒤, **URL 프래그먼트(`location.hash`)** 값을 그대로 `innerHTML`에 대입한다. 프래그먼트는 서버로 전송되지 않고 브라우저에서만 해석되므로 서버 로그나 필터에 걸리지 않으면서도 DOM을 조작할 수 있는 Source-Sink 구조다.

`vuln` 탭에서 `param`, `name`(프래그먼트) 값을 직접 조작해보면 HTML 태그가 그대로 주입되는 것을 확인할 수 있다.

![inj](/assets/img/posts/dom/HTMLinj.png)
위 요청을 보내면 `<h1>HTML Tag Injection</h1>` 태그가 그대로 렌더링되어 HTML Tag Injection이 가능함을 확인할 수 있다.

### flag 탭 & 서버 로직
```py
def check_xss(param, name, cookie={"name": "name", "value": "value"}):
    url = f"http://127.0.0.1:8000/vuln?param={urllib.parse.quote(param)}#{name}"
    return read_url(url, cookie)
```
{: file="admin_bot.py"}

`param`과 `name` 값을 입력받아 `/vuln` 페이지를 봇의 쿠키로 방문한다. `param`은 쿼리스트링으로, `name`은 URL 프래그먼트(`#` 뒤)로 들어가며, 이 `name` 값이 위에서 본 `innerHTML` Sink로 흘러들어가는 구조다.

### 보호기법: CSP nonce
![csp](/assets/img/posts/dom/csp.png)

응답 페이지의 `<script>` 태그에는 랜덤 `nonce` 값이 부여되어 있고, 서버는 아래와 같은 CSP 헤더를 통해 **nonce가 일치하는 스크립트만 실행을 허용**한다.

즉, `param`을 통해 `<script>alert(1)</script>` 를 그대로 주입해도 nonce 값이 없기 때문에 CSP에 의해 실행이 차단된다. 단순 HTML Injection만으로는 스크립트 실행까지 이어지지 않는다.

## 익스플로잇
### 우회 아이디어: 스크립트 가젯(Script Gadget)
| 차단 대상 | 우회 기법 | 핵심 원리 | 실제 적용 |
| :--- | :--- | :--- | :--- |
| CSP `nonce` 검증 | 스크립트 가젯(Script Gadget) | nonce 없는 신규 `<script>` 삽입은 막히지만, **이미 nonce를 가진 신뢰된 script 태그를 나중에 조작**하면 실행 가능 | `param`으로 `id="name"`을 가진 빈 `<script>` 태그를 미리 심어두고, `innerHTML` Sink(`name` 값)로 실제 코드를 채워넣음 |

핵심은 다음과 같다.

1. `param` 값으로 `<script id='name'></script>` 를 주입한다. 이 스크립트 태그는 nonce가 없으므로 그 자체로는 실행되지 않지만, DOM 상에는 `id="name"`인 엘리먼트로 존재하게 된다.
2. 원래 코드는 `document.getElementById("name")`으로 `<pre id="name">` 같은 엘리먼트를 찾도록 의도되어 있었지만, `param`으로 주입한 `<script id='name'>` 이 문서상 더 나중/우선순위에 위치하면서 **타겟이 가로채기(hijack)** 당한다.
3. `name`(URL 프래그먼트) 값이 검증 없이 이 `<script id='name'>` 태그의 `innerHTML`로 들어가면서, **이미 신뢰된(=nonce 검증을 통과할 필요가 없는, DOM API로 직접 채워진) script 태그의 내용물**이 되어 브라우저가 그대로 실행한다.

![hijak](/assets/img/posts/dom/hijak.png)
param값에
```html
<pre id='name'></pre><pre id='name'></pre><pre id='name'></pre><pre id='name'></pre>
```
를 입력하여 맨 처음 id=name인 pre태그에 hash값이 들어가는걸 확인


```text
param -> <script id='name'></script>
name(#뒤) -> location="/memo?memo="+document.cookie;//
```

`innerHTML`(DOM API)로 채워넣은 스크립트 태그속 js는 CSP nonce 검사 없이도 실행된다. 최종적으로 관리자 봇의 쿠키를 `/memo` 엔드포인트로 전송해 탈취한다.

### 결과
![flag](/assets/img/posts/dom/flag.png)

관리자 봇이 위 페이로드가 담긴 URL을 방문하면 쿠키가 `/memo?memo=` 파라미터로 전송되고, 메모 페이지에서 탈취된 쿠키(플래그)를 확인할 수 있다.

## 정리
- **DOM based XSS**는 서버 응답이 아니라 클라이언트 JS의 Source → Sink 흐름 자체에서 발생하므로, 페이지 소스보다 **로드된 JS 코드**를 봐야 찾을 수 있다.
- CSP의 `nonce` 기반 스크립트 화이트리스팅은 **신규 스크립트 태그 삽입**은 효과적으로 막지만, 애플리케이션 로직이 `innerHTML` 등을 통해 **이미 존재하는(또는 공격자가 미리 심어둔) 엘리먼트의 내용을 신뢰 없이 채워넣는 경우** 스크립트 가젯으로 우회될 수 있다.
- 근본적인 해결책은 `innerHTML` 대신 `textContent`를 사용하거나, DOMPurify 등으로 사용자 입력을 블락 하는 것이다.
