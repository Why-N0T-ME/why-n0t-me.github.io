## Introduction

[이전 DHCP 실습](/posts/dhcp)에서는 클라이언트가 IP를 자동으로 할당받는 과정을 다뤘다면, 이번 글에서는 그렇게 할당받은(혹은 정적으로 설정한) IP를 가지고 **패킷이 실제로 목적지까지 어떻게 찾아가는지**를 다룬다. 같은 네트워크 내에서 통신할 때 동작하는 **ARP**부터 시작해서, 서로 다른 네트워크 간 통신을 가능하게 하는 **정적 라우팅(Static Routing)**, 그리고 네트워크 규모가 커졌을 때 필요한 **동적 라우팅(OSPF)**까지 순서대로 실습했다.

특히 정적 라우팅 실습 중에는 "핑은 되는데 실무 방식은 아닌" 설정을 그대로 넘어갈 뻔한 부분이 있었는데, 이 트러블슈팅 과정도 그대로 정리한다.

## Concept: ARP란

**ARP(Address Resolution Protocol)**는 같은 네트워크(브로드캐스트 도메인) 안에서 **IP 주소를 MAC 주소로 변환**해주는 프로토콜이다. 이더넷 프레임은 IP 주소가 아니라 MAC 주소를 기준으로 전달되기 때문에, PC가 통신 상대의 IP 주소만 알고 있어도 실제 프레임을 만들려면 상대방의 MAC 주소가 필요하다.

동작 순서는 간단하다.

1. 송신 장치가 목적지 IP는 알지만 MAC 주소를 모르는 경우, **ARP Request**를 브로드캐스트로 전송한다. ("이 IP를 가진 장치는 자신의 MAC 주소를 알려주세요")
2. 해당 IP를 가진 장치만 자신의 MAC 주소를 담아 **ARP Reply**를 유니캐스트로 응답한다.
3. 송신 장치는 이 매핑 정보를 자신의 **ARP 캐시(테이블)**에 저장해두고, 이후 통신부터는 매번 ARP를 다시 하지 않고 캐시를 사용한다.

실습 중 Packet Tracer의 Simulation 모드로 PC 간 `ping`을 실행하면, 실제 ICMP 패킷이 오가기 직전에 ARP Request/Reply가 먼저 교환되는 것을 Event List에서 확인할 수 있었다. ARP 캐시가 비어있는 최초 통신 시에만 ARP가 발생하고, 이후 ping은 곧바로 ICMP만 오가는 것도 함께 확인했다.

> ARP는 **브로드캐스트 도메인을 넘어가지 못한다.** 즉 다른 네트워크(서브넷)에 있는 장치와 통신하려면 ARP만으로는 부족하고, 이때부터 라우팅이 필요해진다.

## 실습 - 토폴로지 구성

![topology](/assets/img/posts/networking/Routing/topology.png)
> PC0/PC1(192.168.103.0/24) — Switch0 — NAT-1(Router0) — Serial — Router1 — Serial — NAT-2(Router2) — Switch1 — PC2/PC3(10.23.10.0/24)

| 구간 | 대역 | 비고 |
| :--- | :--- | :--- |
| NAT-1 ↔ PC0, PC1 | 192.168.103.0/24 | NAT-1의 FastEthernet0/0 = .1 |
| NAT-1 ↔ Router1 | 10.10.20.0/24 | NAT-1 = .1, Router1 = .2 |
| Router1 ↔ NAT-2 | 10.10.30.0/24 | Router1 = .2, NAT-2 = .1 |
| NAT-2 ↔ PC2, PC3 | 10.23.10.0/24 | NAT-2의 FastEthernet0/0 = .1 |

3개의 라우터가 직렬로 연결된 구조로, 라우터 1대씩 건너 서로 다른 네트워크에 있는 PC끼리 통신하는 것이 목표다.

## 실습 - 정적 라우팅(Static Routing)

### 1차 설정과 트러블슈팅: "되긴 하지만 잘못된" next-hop

처음 각 라우터에 정적 경로를 등록하고 `show ip route`로 확인했을 때 결과는 다음과 같았다.

![router0-recursive](/assets/img/posts/networking/Routing/router0-recursive-nexthop.png)
> NAT-1의 라우팅 테이블. `10.23.10.0/24`로 가는 경로의 next-hop이 `10.10.30.2`로 되어 있다.

```
S    10.10.30.0/24 [1/0] via 10.10.20.2      ← 정상 (Router1 인터페이스)
S    10.23.10.0/24 [1/0] via 10.10.30.2      ← 문제
```

`10.10.30.2`는 NAT-1에 **직접 연결되지 않은 주소**다(이건 NAT-2의 인터페이스 주소다). NAT-2도 마찬가지로 반대 방향에 같은 패턴의 경로가 잡혀 있었다.

![router2-recursive](/assets/img/posts/networking/Routing/router2-recursive-nexthop.png)
> NAT-2의 라우팅 테이블. `192.168.103.0/24`로 가는 경로의 next-hop이 자신과 직접 연결되지 않은 `10.10.20.2`로 되어 있다.

**> 트러블슈팅**
Ping은 정상적으로 성공했다. IOS가 재귀적으로(recursive lookup) `10.10.30.2`가 어떤 인터페이스를 통해야 도달 가능한지 다시 한번 찾아서 최종적으로는 경로를 완성하기 때문이다. 하지만 이는:

- 불필요한 재귀 조회로 라우터 부하가 늘어나고
- 중간 경로가 바뀌면 연쇄적으로 영향을 받으며
- 직관적으로 어떤 경로로 나가는지 파악하기 어려워진다

즉 "동작은 하지만 실무에서는 쓰지 않는" 설정이었다. 정적 경로의 next-hop은 **항상 물리적으로 바로 인접한 라우터의 인터페이스 주소**를 지정해야 한다. 실제로 중간에 있는 Router1은 처음부터 이 원칙대로 설정되어 있었다.

![router1-correct](/assets/img/posts/networking/Routing/router1-static-correct.png)
> Router1의 라우팅 테이블. 두 정적 경로 모두 next-hop이 바로 옆에 물리적으로 연결된 인터페이스 주소(`10.10.30.1`, `10.10.20.1`)로 되어 있다.

### 개선: Stub 구간은 Default Route로

NAT-1과 NAT-2는 나가는 길이 하나뿐인 **스텁(stub) 라우터**다. 이런 구조에서는 목적지 네트워크마다 정적 경로를 하나씩 등록하는 대신, **디폴트 라우트(0.0.0.0/0) 하나**로 충분히 커버할 수 있다. 목적지가 늘어나도 매번 경로를 추가할 필요가 없어 실무에서 더 널리 쓰이는 방식이다.

```
NAT-1(config)#ip route 0.0.0.0 0.0.0.0 10.10.20.2
NAT-2(config)#ip route 0.0.0.0 0.0.0.0 10.10.30.2
```

**> 트러블슈팅: 오타로 인한 문법 오류**

![typo-error](/assets/img/posts/networking/Routing/typo-error.png)
> `ip route 0.0.0.0 0.0.0.0. 10.10.20.2` — 두 번째 서브넷 마스크 뒤에 마침표(`.`)가 잘못 붙어 `Invalid input`이 발생했다.

`ip route [목적지 네트워크] [서브넷 마스크] [next-hop]` 형식에서 마스크 뒤에 마침표가 하나 더 들어가 IOS가 문법을 인식하지 못한 경우였다. 마침표를 제거하고 다시 입력하니 정상적으로 반영됐다.

![router0-default](/assets/img/posts/networking/Routing/router0-default-route.png)
> NAT-1에 정상적으로 default route가 반영된 모습. `Gateway of last resort is 10.10.20.2 to network 0.0.0.0`

![router2-default](/assets/img/posts/networking/Routing/router2-default-route.png)
> NAT-2도 동일하게 `10.10.30.2`를 next-hop으로 하는 default route가 반영됐다.

### 통신 확인

PC2에서 PC1로 ping을 실행한 결과, 라우터 3대(Router2 → Router1 → Router0)를 모두 거치는 왕복 경로가 정상적으로 성립했다.

![ping-event1](/assets/img/posts/networking/Routing/ping-event1.png)
![ping-event2](/assets/img/posts/networking/Routing/ping-event2.png)
> Event List에서 ICMP 요청이 Router2 → Router1 → Router0 → PC1까지, 응답이 반대 순서로 정상적으로 오가는 것을 확인했다.

## 개념정리: 왜 동적 라우팅이 필요한가

정적 라우팅은 소규모 네트워크에서는 명확하고 예측 가능하지만, 다음과 같은 한계가 있다.

- 네트워크(목적지)가 늘어날수록 관리자가 수동으로 등록해야 할 경로가 계속 늘어난다.
- 회선 장애 등으로 토폴로지가 바뀌어도 라우터가 스스로 대체 경로를 찾지 못한다. 관리자가 직접 경로를 수정해줘야 한다.

이 문제를 해결하기 위해 라우터들이 서로 자동으로 경로 정보를 교환하고, 최적 경로를 스스로 계산하는 **동적 라우팅 프로토콜**을 사용한다. 이번 실습에서는 그중 **OSPF(Open Shortest Path First)**를 사용했다.

### OSPF 핵심 개념

| 개념 | 설명 |
| :--- | :--- |
| **Area** | OSPF가 관리하는 논리적 구역. 소규모 네트워크는 백본 영역인 `area 0` 하나로 충분하다 |
| **Router ID** | 각 OSPF 프로세스를 구분하는 고유 식별자. 별도 지정하지 않으면 라우터의 가장 높은 인터페이스 IP가 자동으로 선택된다 |
| **Hello / Neighbor** | 서로 인접한 라우터끼리 Hello 패킷을 주기적으로 교환하며 이웃(Neighbor) 관계를 맺는다 |
| **Adjacency State** | Down → Init → 2-Way → ExStart → Exchange → Loading → **Full** 순서로 진행되며, Full이 되어야 링크 상태 정보 교환이 완료된 것이다 |
| **Administrative Distance(AD)** | 여러 라우팅 정보 출처 중 어느 것을 우선할지 결정하는 값. Static route는 AD 1, OSPF는 AD 110으로, **AD가 낮을수록 우선**된다 |

> OSPF로 전환할 때 기존 정적 경로(특히 default route)를 지우지 않으면, OSPF가 같은 목적지 경로를 학습해도 AD가 더 낮은 static route가 계속 우선 적용되어 무시된다. 반드시 `no ip route ...`로 기존 static route를 먼저 제거해야 한다.
{: .prompt-warning }

## 실습 - OSPF 설정

### 1. 기존 static route 제거 후 OSPF 등록

```
NAT-1(config)#no ip route 0.0.0.0 0.0.0.0 10.10.20.2
NAT-1(config)#router ospf 1
NAT-1(config-router)#network 192.168.103.0 0.0.0.255 area 0
NAT-1(config-router)#network 10.10.20.0 0.0.0.255 area 0
```
```
Router1(config)#router ospf 1
Router1(config-router)#network 10.10.20.0 0.0.0.255 area 0
Router1(config-router)#network 10.10.30.0 0.0.0.255 area 0
```
```
NAT-2(config)#no ip route 0.0.0.0 0.0.0.0 10.10.30.2
NAT-2(config)#router ospf 1
NAT-2(config-router)#network 10.23.10.0 0.0.0.255 area 0
NAT-2(config-router)#network 10.10.30.0 0.0.0.255 area 0
```

`network [네트워크] [와일드카드 마스크] area [영역번호]`에서 와일드카드 마스크는 서브넷 마스크를 반전시킨 값이다(`255.255.255.0` → `0.0.0.255`).

**> 트러블슈팅: 특권 모드에서 바로 명령어 입력**

```
NAT-1#router ospf 1
             ^
% Invalid input detected at '^' marker.
```

`conf t`(전역 설정 모드)로 진입하지 않은 상태에서 `router ospf 1`을 입력해 발생한 오류였다. `NAT-1#`은 특권 모드(privileged EXEC)라 이 명령어 자체를 인식하지 못한다. `conf t`로 먼저 진입한 뒤 다시 입력하니 정상적으로 처리됐다.

![ospf-config-mistake](/assets/img/posts/networking/Routing/ospf-config-mistake.png)
> 왼쪽(NAT-1)에서 `conf t` 없이 `router ospf 1`을 입력해 에러가 난 후, 바로 아래에서 `conf t`로 재진입해 정상 설정한 로그. 오른쪽(NAT-2)은 처음부터 올바른 순서로 설정한 모습.

**> 트러블슈팅: Neighbor가 안 잡히는 이유**

Router1에서 OSPF 설정 직후 `show ip ospf neighbor`, `show ip route ospf`를 실행했지만 결과가 비어있었다.

![ospf-neighbor-empty](/assets/img/posts/networking/Routing/ospf-neighbor-empty.png)
> `show ip protocols`로 보면 OSPF 프로세스 자체는 정상 설정되어 있지만(Routing for Networks에 두 대역 모두 표시), neighbor 목록은 비어있다.

이 시점에는 **NAT-1과 NAT-2가 아직 OSPF 설정 전**이었다. OSPF는 양쪽 라우터가 모두 설정되어 Hello 패킷을 주고받아야 이웃 관계가 성립하므로, 한쪽만 설정된 상태에서는 당연히 neighbor가 비어있을 수밖에 없다.

### 2. 전체 설정 완료 후 확인

세 라우터 모두 OSPF 설정을 마친 뒤 Router1에서 다시 확인하니, adjacency가 정상적으로 완료됐다.

![ospf-neighbor-full](/assets/img/posts/networking/Routing/ospf-neighbor-full.png)
> `%OSPF-5-ADJCHG` 로그로 두 이웃(NAT-1, NAT-2)이 모두 LOADING → **FULL** 상태로 전환된 것을 확인. `show ip ospf neighbor` 결과에도 두 이웃 모두 State가 `FULL`로 표시된다.

```
%OSPF-5-ADJCHG: Process 1, Nbr 192.168.103.1 on Serial0/3/0 from LOADING to FULL
%OSPF-5-ADJCHG: Process 1, Nbr 10.23.10.1 on Serial0/3/1 from LOADING to FULL
```

Point-to-point 링크(Serial)는 DR/BDR 선출 과정이 없기 때문에 State가 `FULL/-`로 표시되는 것이 정상이다. (이더넷 멀티액세스 구간이었다면 `FULL/DR`, `FULL/BDR` 형태로 표시된다.)

### 3. Convergence(수렴) 시간 관찰

Static route를 제거한 직후, OSPF의 adjacency가 완전히 맺어지기 전에 PC2에서 PC1로 ping을 실행해봤다.

![convergence-ping-fail](/assets/img/posts/networking/Routing/convergence-ping-fail.png)
> 처음 두 번의 ping은 `Request timed out.` / `Destination host unreachable.`로 실패했고, 세 번째 시도부터 정상 응답을 받았다.

같은 시점의 Event List를 보면, ICMP 대신 **OSPF 패킷(Hello, LSA 등)만 반복적으로 오가는 것**을 확인할 수 있었다.

![convergence-ospf-events](/assets/img/posts/networking/Routing/convergence-ospf-events.png)
> 라우터 간에 OSPF 패킷만 교환되고 있는 구간. 이 시점에는 아직 라우팅 테이블에 경로가 설치되지 않아 ping이 실패한다.

**> 트러블슈팅 정리**: Static route를 지운 시점과 OSPF가 실제로 라우팅 테이블에 경로를 설치하는 시점 사이에는 공백이 있다. OSPF는 Hello 교환 → 이웃 확인 → 링크 상태 정보(LSA) 교환 → SPF 알고리즘으로 최적 경로 계산 → 라우팅 테이블 반영이라는 단계를 거치기 때문에, 설정 즉시 반영되는 static route와 달리 일정한 **수렴(convergence) 시간**이 필요하다. `show ip ospf neighbor`의 State가 `FULL`이 되는 시점과, `show ip route`에 `O`로 시작하는 경로가 나타나는 시점, 그리고 ping이 정상적으로 통과하는 시점이 정확히 일치하는 것도 함께 확인했다.

## 요약

* **ARP**: 같은 네트워크 내에서 IP 주소를 MAC 주소로 변환하는 프로토콜이며, 브로드캐스트 도메인을 넘어가지 못한다.
* **정적 라우팅**: 소규모 네트워크에서 명확하지만, next-hop은 반드시 물리적으로 인접한 라우터의 인터페이스 주소로 지정해야 하며(재귀적 조회 지양), 스텁(stub) 구간에는 개별 경로 대신 default route를 쓰는 것이 실무에 가깝다.
* **동적 라우팅(OSPF)**: 라우터끼리 Hello/LSA를 교환해 스스로 최적 경로를 계산하며, static route보다 관리 부담은 적지만 adjacency 형성과 라우팅 테이블 반영까지 일정한 **convergence 시간**이 소요된다는 차이가 있다. OSPF로 전환할 때는 AD 값 차이로 인해 기존 static route를 먼저 제거해야 한다.

다음 글에서는 이 토폴로지를 이용해 **GRE 터널링과 VPN(IPSec)** 구현을 다룰 예정이다.
